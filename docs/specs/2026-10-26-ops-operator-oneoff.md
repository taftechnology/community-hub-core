# Spec: Ops operator one-off — grant, revoke and recover operators, and the operator runbook

Slug: ops-operator-oneoff
Status: approved (2026-10-26, Abdus Salam)
Depends on: `docs/specs/2026-10-22-ops-operator-identity.md` (PR #62), `docs/specs/2026-10-25-ops-console-api.md` (PR #63)
Architecture refs: §11.4; ADR 0015 (interim single-owner recovery); AGENTS.md §1 rules 1, 5, 8; §6 Residency; §13 (runbooks)

## Problem

The identity module can grant, revoke and recover operators (PR #62), and the ops routes can enrol and sign them in (PR #63), but nothing in a deployed environment can call `grantOperator`. The operator spec says only the owner grants, through an owner-run `ops-operator` one-off (O2), with its input in the one fixed provision secret (O3, O16), and ADR 0015 says the runbook section for recovery must exist before the first production use. Neither exists. Two small follow-ups from PR #62's review are also open.

## Behaviour

1. The owner checks the secret name is free, generates the enrolment code (B6), creates the secret, runs the one-off, reads the one word, and deletes and verifies the secret (B7).
2. **grant** → `granted`: the user exists (created if needed) and holds an open grant for the named roles with a 24-hour window. The operator enrols on the ops host with an email code and the enrolment code.
3. **revoke** → `revoked`: every grant and every operator and enrolment session of the user is revoked and their ops passkeys deleted (operator spec O11, O15). Tenant access is untouched.
4. **recover** → `recovered`: in one transaction, revoke as above, record `recovery_regrant`, and grant again with a new code and window (O14, ADR 0015). The operator enrols two new passkeys.
5. Every failure prints one fixed stderr word and exits 1. Identity's grant, revoke and recover each run in one transaction. A `grant` that creates a user and is then refused by identity for a reason B3a cannot see (a conflicting open or active grant cannot happen for a new user; a database failure can) leaves only that identity user row; the runbook says re-running the same `grant` reuses it.

## Data

No new table or column, no migration. Writes go through existing identity functions: possibly one `identity.users` row (address encrypted, blind index), and `operator_grants`, `operator_events`, `sessions` and `passkey_credentials` changes as the operator spec describes. The secret value holds an address and an enrolment code (`confidential`); it exists only between **Create** and **Delete and verify**, under the customer-managed secrets key, in `ap-southeast-2`.

**Residency.** The one-off runs as an ECS task in `ap-southeast-2`; the secret, keys and database are there. Nothing leaves Australia.

**Logs.** Only the fixed words. The runbook never records an ARN, account id, hostname, secret name, address or code.

**Single-person risk (ADR 0015).** Whoever holds the owner's AWS access and the provision secret can grant or recover any operator. Every grant, revoke and recovery is recorded in `identity.operator_events`. Review by 2027-04-30 or when a second `platform_security` person joins.

## Contracts

No route, event, permission or website key. A new process entry point `node /app/ops-operator.js`, reading `PROVISION_SECRET_ARN` and the service env it shares with `provision-owner`. `provision-owner` gains one stderr outcome (`shape`). Identity public API: unchanged.

## Risks

- **The secret is used by the wrong tool.** Mutual refusal before any query (pins 1, 2); the runbook's name-is-free check and "never at the same time".
- **The enrolment code or address leaks.** Generated offline, shown once, never typed as an argument, never printed by the tool (pin 3), secret force-deleted after every run, never in evidence.
- **A stray identity user.** `revoke` and `recover` never create (pin 5); `grant` validates before creating (pin 6).
- **The pre-check drifts from identity.** A test runs the same samples through both (B3a).
- **Recovery by one person.** ADR 0015's accepted risk; recorded events and the review date.
- **Size.** Estimated 300–400 source lines, 450–600 test lines and a runbook of about 250 lines: about 1,000–1,250 changed lines in total, over the ~800-line guide (AGENTS.md §3). The runbook cannot be split from the tool (the tool is unusable without it, and ADR 0015 needs it before production). B8 and B9 (about 40 source and 60 test lines) are the last code task and can move to a `fix/` branch if the owner prefers. Two code areas (`apps/api`, identity). **Owner to accept the overrun, or move B8 and B9 out.**
