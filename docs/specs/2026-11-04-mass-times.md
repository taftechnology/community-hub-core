## Problem

A parish cannot publish when its Masses and other services are held. Laravel has a Mass Times screen under Engagement: one editor, "Schedule Content", and a Save button. The text shows on the public Mass Timings page and in the mobile app. Core has no `engagement` module, no screen, and nothing a website or the Parish Hub app can read. The roadmap says this is the next Phase 2 journey and the first public-facing one, so it also sets the pattern for the other three Engagement screens and for every external collection after it.

## What Laravel does (read from the Laravel code by Abdus, 2026-11-05)

- Mass Times is **one rich-text block per site**, stored as the setting `mass_timings` in `website_settings` (`MassTimingController.php`). It is not rows, and has no weekday, time or status fields.
- The admin screen (`resources/js/Pages/Dashboard/MassTimings.jsx`) is one editor, "Schedule Content", and a Save button. `SimpleRichTextEditor` has quote, code, link and image switched off, so the tools are headings, bold, italic and lists.
- The public Mass Timings page shows the same text through the site template (`PagesController.php` near line 1031).
- The mobile app reads it raw from `GET /mobile-app/mass-timings`, which returns `{ success: true, data: "<html>" }` (`MobileAppController::apiMassTimings`).
- `mobile_app_services` is unrelated: it has only `id` and timestamps, and "Services" on the mobile home means "Sacraments & more".

**Owner decision (Abdus, 2026-11-05):** keep the same shape as Laravel. One rich-text block per community. No weekly or dated rows. There is no Mass Times board in the design canvas, so the screen is that one editor plus Save, built from the design system's components. The canvas dashboard quick action still reads "Update Mass Timings"; core uses "Mass Times".

- **The sanitiser.** A pure function `sanitiseServiceTimesHtml(input)` in the engagement domain. It turns any input string into HTML that uses only the allow-list below, and it is called **inside** `saveServiceTimes`, not in the route, so no caller can skip it. It never rejects markup it does not like: it keeps the text and removes the tag. Allow-list, matching the editor's tools:
  - Tags: `p`, `br`, `h1`, `h2`, `h3`, `h4`, `strong`, `em`, `ul`, `ol`, `li`. `b` becomes `strong` and `i` becomes `em`. Any other tag is unwrapped: the tag goes, its allowed contents stay (`<div><p>x</p></div>` becomes `<p>x</p>`). The tags `script`, `style`, `iframe`, `object`, `embed`, `svg`, `math`, `template`, `noscript`, `textarea` and `option` are dropped **with their content**, including any allowed tag nested inside them (`<svg><p>x</p></svg>` becomes nothing).
  - **No attributes of any kind** on any tag: no `href`, `src`, `style`, `class`, `id`, `on*`, `data-*`, and not `start` on `ol` (a numbered list that starts at 5 renumbers from 1; the screen's hint says so).
  - Comments, processing instructions and CDATA are dropped.
  - **Library configuration (D8 option a).** `sanitize-html` with `allowedTags` as above, `allowedAttributes: {}` (the empty object; `false` would allow every attribute, and a test pins the difference), `disallowedTagsMode: "discard"`, `transformTags` for `b` and `i`, `nonTextTags` set to the list above (setting it replaces the library default, so the default `script`, `style`, `textarea` and `option` are repeated), no `exclusiveFilter` (`nonTextTags` already drops a container tag with everything inside it), no `textFilter`, and `allowVulnerableTags` left at the library default. The server also removes U+0000 and replaces lone surrogates with U+FFFD before cleaning, so what `save` returns is what `get` returns and the database accepts it. With zero attributes, only allowed tags and escaped text in the output, a parser difference can reorder elements but cannot create a script or a handler.
  - **Empty normalisation.** A result with no non-whitespace text and no list item becomes `""` (`<p></p>`, `<p><br></p>`, `<h1> </h1>`, `<ul><li><p></p></li></ul>`). Tiptap serialises an empty document as `<p></p>`, so without this the stored and public value would be non-empty.
  - **The cap** is on the sanitised HTML string, in UTF-16 units as JavaScript's `.length` measures it: 20,000. The editor measures `editor.getHTML().length` against the same number. The server enforces the cap **after cleaning**, in `saveServiceTimes`: input that sanitises to more than 20,000 units is `invalid_input`, and input longer than that which sanitises to 20,000 or fewer is accepted. Zod caps the raw `html` field at 120,000 units only, so the sanitiser never parses a string larger than the request body can carry. Both sides of the cap are tested. Longer cleaned output is never silently cut. The database check (`char_length ≤ 20000`, code points) is a backstop, never the limit a user meets.
  - Sanitising is idempotent over the fixture corpus (`sanitise(sanitise(x)) === sanitise(x)` for every corpus entry). It is **not** idempotent for every possible input: a second pass can re-nest malformed list or heading structure (for example `<li><div><li>a</div>` gives `<li><li>a</li></li>`, then `<li></li><li>a</li>`). Every output of every pass stays inside the allow-list with no attributes, so this changes structure only, never safety. It is also not claimed to be stable across a Tiptap round trip (see Behaviour).

## Behaviour

- A community has **one Mass Times block**: formatted text (headings, bold, italic, bulleted and numbered lists). Whatever is saved is public. There is no draft and no hidden state, as in Laravel.
- Staff with `service_times.manage` open Engagement → Mass Times and see the editor with the saved text, or an empty editor with the pack's placeholder when nothing was saved.
- **Save** sends the editor's HTML. The server sanitises it, stores the sanitised result, and returns it. The screen replaces the editor content with what the server returned, so what the staff member sees is exactly what is public. After a save the screen shows a "Saved" status message that a screen reader announces.
- **Empty save.** Saving an empty editor stores an empty block. The editor serialises an empty document as `<p></p>`; the sanitiser normalises any result with no text to `""`, so the stored value and the public projection are `html: ""` and the website shows nothing. It is not an error.
- Text that sanitises to nothing (for example only a script) is stored as empty, and the screen shows what the server returned.
- **What the editor shows after a save.** The server's HTML is loaded back into the editor, which may re-serialise it slightly (`<li>x</li>` becomes `<li><p>x</p></li>`, `<br />` becomes `<br>`). The screen's "unsaved changes" baseline is `editor.getHTML()` captured right after that load, never the server string, so the leave prompt does not fire after a save. A test pins it: load, then leave, gives no prompt.
- **Optimistic concurrency.** The row has a `version`. No row reads as version `0`. `save` carries the expected `version`, a non-negative integer (a negative or non-integer value is `invalid_input` at Zod). The repository decides, in one transaction through the RLS-scoped helpers:
  - expected `0`: `insert … on conflict (org_id, community_id) do nothing returning version`, at version `1`. No row returned means a row already exists, which is `version_conflict`. This is the pattern `usage/infrastructure/record.ts` already uses under RLS; it needs only the `INSERT` grant, and avoids a unique violation aborting the transaction (a plain insert would surface a 500, not a 409).
  - expected `n > 0`: `update … where org_id = :org and community_id = :community and version = :expected`, setting `content_html`, `version = version + 1` and `updated_at`. Zero rows returned (no row, a different version, or a writer that won in between) is `version_conflict`.
  - Every "row missing or version changed" outcome is the same `version_conflict`, so no select is needed first; a foreign organisation's or community's row is invisible under RLS and answers the same.
  - The API answers `version_conflict` with an empty `409`, as the existing routes do. The screen keeps the staff member's text, says another change was saved first, and offers to reload the saved text. It never overwrites silently.
- The text is **plain stored HTML**, sanitised on write. Reads do not re-render it. Jellycube and the mobile app render the string, so the allow-list is the protection (see Risks).
- Error states: a failed save keeps the editor content and shows a fixed message; it prints no server text, SQL, hostname or stack. A 402 (billing read-only) and a 403 (no permission) show the existing messages. A text over the 20,000-character cap shows a fixed message and is not sent. A stale load after a save is guarded by the generation guard from the earlier admin screens, pinned by a test that fails without it.
- Unsaved changes: leaving the screen with unsaved edits asks to confirm. No existing admin screen has this guard (nothing in `apps/admin/src` uses `beforeunload` or `useBlocker`), so this chunk introduces both: `beforeunload` for closing the tab and the router's `useBlocker` (the admin uses `createBrowserRouter`) for in-app navigation, each with tests. No autosave.
- No offline behaviour. The admin is online-only today.
- The screen shows "Mass Times" because the faith-church pack says so. Nothing in the code path names Mass.

## Data

New `app` table, community-scoped, **one row per community**. Every column is added to `dataClasses` and `manifest.test.ts` in the migration task.

`app.service_times`

| Column         | Type                                             | Class    |
| -------------- | ------------------------------------------------ | -------- |
| `org_id`       | `uuid not null`                                  | internal |
| `community_id` | `uuid not null`                                  | internal |
| `content_html` | `text not null default ''`, check length ≤ 20000 | public   |
| `version`      | `integer not null default 1`                     | internal |
| `created_at`   | `timestamptz not null`                           | internal |
| `updated_at`   | `timestamptz not null`                           | internal |

- **Content is public. It holds no personal data** (owner, 2026-11-05; architecture §12.1 lists service times as `public`). Classes follow the precedent in every other manifest: ownership and bookkeeping columns are `internal`. The projection allow-list is **exactly** the `public` set: `content_html`, shown to clients as `html`. A test derives the allow-list from `dataClasses` and fails if any non-`public` column appears in it. The SQL for `getPublishedServiceTimes` names the one column.
- **Free text caution.** A parish could type a name or phone number into the text. The class stays `public` because the column is meant to be shown. Mitigation: the hint under the editor, and no content in logs or audit lines. The reviewer checks that no log or audit line carries `content_html` or its length.
- Primary key `(org_id, community_id)`: one block per community, and the key starts with `org_id`. No other unique key and no index. No foreign key to a person.
- Row level security `community_isolation`, `FOR ALL TO public`, `USING` and `WITH CHECK` both `org_id = current_setting('app.org_id')::uuid and community_id = current_setting('app.community_id')::uuid`. `FORCE ROW LEVEL SECURITY`.
- **Grants.** Written literally in the migration as `0017` does (table-level `UPDATE` was already revoked in `0005`):
  `REVOKE UPDATE, DELETE, TRUNCATE ON app.service_times FROM app;`
  `GRANT SELECT, INSERT ON app.service_times TO app;`
  `GRANT UPDATE (content_html, version, updated_at) ON app.service_times TO app;`
  so `org_id`, `community_id` and `created_at` can never be rewritten and no flow deletes the block (an emptied block is stored as empty; `0014` revokes `DELETE` on `app.groups` the same way). `identity` and `platform` get nothing. A `schema.test.ts` `toContain` pins the three statements, as `groups/db/schema.test.ts` does. A later per-community restore cannot use `app` to delete, as with persons.
- No column is encrypted. The block is public, nothing sorts or aggregates on it, and encrypting public content would only add keys. No blind index. No person column, so no minor's data can be held or joined.
- The sanitiser's allow-list is **not** a column or a setting. It is code and a contract, so changing it is a reviewed change with its test.

## Rules touched

- **Sanitising (new, named by the owner).** The sanitiser removes every tag outside the allow-list, every attribute, scripts, styles and comments. Because Jellycube and the mobile app render this text, a must-fail test feeds hostile input and asserts none of it survives (see Tests), and the plan lists the source change that must make that test fail.
- **Request size (D9).** The save route reads a body of up to **128 KiB** (`largeBody: "content"`), thirty-two times the 4,096-byte limit every other POST has. The body is read **before sign-in, entitlement and permission are checked**, so an unauthenticated caller can make the server read up to 128 KiB on that one route. The existing 30-second request timeout (`REQUEST_TIMEOUT_MS`) still applies to a slow body. The limit is allowed only on `POST /v1/engagement/service-times/save`, never on the webhooks hostname, and `assertRoutes` and a route-list test reject it anywhere else. A body over the limit returns 413.
- Tenancy: one `app` table with `org_id`, `community_id`, RLS and `FORCE`. Scope comes from the transaction only; no function takes an organisation or community as an argument.
- Children (§1 rule 4, §12.3): the table holds no person data, no names and no household link.
- §1 rule 5: errors are fixed codes. Audit events carry ids only. No content in a log, trace or URL.
- Public content (§12.1, §15.5): `public` class, allow-list projection.
- Permissions: `service_times.manage` in the catalogue, granted to `community_admin`, `org_owner`, `org_admin` and `content_editor` (D3), and available to custom roles (D6). See Permission plumbing in Scope.
- Entitlements: `module.engagement` (already in `plans.starter`) gates the API, the nav and the screen.
- Residency, consent, retention: none new. Public data, Australian region.

## Contracts

## Risks

- **Stored script injection (XSS).** Jellycube and the mobile app render this text, so a script or event handler that survives the sanitiser runs on every parish site. Mitigations: the allow-list above, no attributes at all, the sanitiser called inside `saveServiceTimes` so no caller skips it, the idempotence test, the must-fail hostile-input test, and the importer using the same function. A weakened allow-list must fail a test. Residual: a row written straight into the database bypasses the sanitiser; only the engagement module's `INSERT` and `UPDATE` grants reach the table, and no other code writes it.
- **The sanitiser library changes behaviour.** A version bump could widen what passes. The hostile-input suite is the guard; the dependency is pinned exactly and its upgrades go through the dependency-bump lane with this suite green.
- **Cross-tenant read or write.** Scope from `current_setting` only; policy on `USING` and `WITH CHECK`; `FORCE`; tests with two organisations and with two communities in one organisation, on both routes and on the projection.
- **Lost update.** The version match on update, `insert … on conflict do nothing` for the first save, bump on every write; tests for a stale version, a first-save race and a missing row with a non-zero expected version.
- **Larger request body (D9).** The save route reads up to 128 KiB **before sign-in is checked**, so an unauthenticated caller can make the server read that much on one route. That widens the denial-of-service surface a little. Mitigations: the limit applies to that one route only, never on the webhooks hostname; `assertRoutes` rejects `largeBody: "content"` anywhere else and a route-list test fails if another route gets it; the existing 30-second request timeout still applies to a slow body; an over-limit body is cut off with 413 and the connection is destroyed, as the webhook route does.
- **The editor writes what the server drops.** Fixed by configuring the editor's schema to the allow-list and by loading the server's HTML back after a save. The numbered-list start number is the one known loss, stated in the hint.
- **A non-public field on the public projection.** SQL names the one column; the allow-list is derived from `dataClasses`; a must-fail test feeds a row object with extra properties (`org_id`, `community_id`, `version`, a `confidential` field, a minor flag) and asserts none reach the output.
- **Personal data typed into the text.** Mitigated by the hint and no logging; not preventable in code.
- **Permission catalogue change.** A new key in a closed list touches the access CHECK, two lists, and several pins. The migration's recovery note and the changed tests are in Scope; a missed copy fails a pin.
- **A second route list drifting.** The new routes are added to `productionRoutes()` only, once #74 is on `main`. If #74 is not merged, task 1 does not start.
- **The label drifting into code.** The boundary test above fails on `mass` in a path, route, key or identifier.
- **Packaging.** The new packages must be in `pnpm-workspace.yaml`, the lockfile, `apps/api/package.json`, the Dockerfile filter and `image.test.ts`'s name list; the admin gets the faith-church dependency.
- **Schema loader.** `engagementTables` imports no value from `@community-hub/db`; `generate.test.ts` covers it. The turbo input fix means a schema change invalidates the cached db test.
- **Public contract freeze.** `{ html }` becomes the shape Jellycube and the mobile app bind to, and the allow-list is part of what they can rely on. Widening the allow-list is additive; narrowing it or changing the shape means `/v2`.
- **Editor accessibility.** A rich-text editor is the hardest component to make accessible. It gets axe, a keyboard test of the toolbar and a test for the accessible name. A failing axe test blocks the merge (WCAG 2.2 AA is a gate).
- **Laravel's real editor output.** The allow-list matches the tool list the owner read from the code. Real stored values may use other tags or inline styles. The importer chunk runs real exports (on non-production data) through the sanitiser and reports what was dropped before cutover; text is always kept, so the loss is formatting only.

## Tests

- Unit, sanitiser: each allowed tag survives; `b` and `i` become `strong` and `em`; other tags are unwrapped and their allowed contents kept (`<div><p>x</p></div>` becomes `<p>x</p>`); `script`, `style`, `iframe`, `svg`, `math`, `template`, `object`, `embed` are removed with their content, including a nested allowed tag (`<svg><p>x</p></svg>` becomes nothing); every attribute is stripped, including `href`, `src`, `style`, `class`, `id`, `on*`, `data-*` and `start`; `allowedAttributes` is the empty object (a test fails if it were `false`); `javascript:` and `data:` URLs, entity-encoded and nested payloads, unclosed and stray tags and comments do not survive. Fixtures also cover `</br>`, `<br/>`, `<BR>`, `<p>` inside `<li>`, `ul > li > ol`, `&nbsp;` (kept as U+00A0), `&lt;script&gt;` (stays escaped text) and a stray `</p>`. Sanitising twice equals sanitising once over the whole corpus. `<p></p>`, `<p><br></p>`, `<h1> </h1>` and `<ul><li><p></p></li></ul>` become `""`. The cap is enforced on the cleaned output: input over 20,000 units that cleans to 20,000 or fewer is accepted, cleaned output of 20,001 is `invalid_input`, and a raw `html` over 120,000 units is rejected at Zod; plain text and empty input pass.
- **Must-fail hostile suite, structural.** A list of hostile inputs; each output is parsed with `jsdom` 30.1.1 (a dev dependency of the engagement package, the version the repo already uses) and the test asserts: every element is in the allow-list, every element has zero attributes, and there is no comment, CDATA or processing-instruction node. It does not grep for words such as `href` or `javascript:`, because safe text may contain them. `<script` and `on…=` are checked as substrings only, since escaping makes them impossible in the output. An integration test stores `<p onclick=x>a</p><script>b</script>` through `saveServiceTimes` and reads back `<p>a</p>`; removing the sanitiser call fails it.
- Unit, other: input validation (version, length), the projection allow-list derived from `dataClasses`, terminology lookup (singular and plural), the label boundary test.
- Integration (Docker test database): first save inserts at version `1`; save with the right version increments; a stale version, expected `0` with an existing row, and a non-zero expected version with no row all give `version_conflict` and change nothing; two concurrent first saves leave one row, one success and one `version_conflict` (not an unmapped error); an empty save stores an empty block; the stored value equals the sanitised value, not the input; `getServiceTimes` returns version `0` and empty html with no row; `getPublishedServiceTimes` returns only the allow-listed column; two organisations and two communities in one organisation, no read or write crosses; the round trip from the database to the projection to `serviceTimesPublicSchema`; audit rows hold ids and no text; `saveServiceTimes` adds one to `module.engagement` usage and a rejected save adds nothing.
