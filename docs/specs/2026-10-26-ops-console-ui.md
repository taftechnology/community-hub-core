# Spec: Ops console UI — enrolment, passkey sign-in and the directory in `apps/ops`

Slug: ops-console-ui
Status: draft
Depends on: `docs/specs/2026-10-25-ops-console-api.md` (merged in PR #63), `docs/specs/2026-10-26-ops-operator-oneoff.md` (merged in PR #64)
Architecture refs: §8.5 Ops console (`architecture.md:484`), §11.4, §19 Ops console, §20; D16; ADR 0015; AGENTS.md §1 rules 5, 6, 8; §6 API and UI, Cost

## Problem

The ops host can serve a bundle (`apps/api/src/ops-static.ts`) and answers every ops route (`apps/api/src/ops-routes.ts`). The owner can grant an operator with the `ops-operator` one-off (PR #64). But there is no bundle. A granted operator has no page on which to enter their codes, register passkeys, sign in or read the directory, and the image sets no `OPS_STATIC_DIR`.

Reading the API for this spec found two gaps in `POST /v1/ops/passkey/register/options` that the UI cannot work around:

1. **No `rp.name`.** Identity returns `rp: { id }` only (`passkey.ts` `beginPasskeyRegistration`, the `rp` field), and the route forwards it (`ops-routes.ts` register-options handler). `PublicKeyCredentialRpEntity.name` is a required WebIDL member, so `navigator.credentials.create` throws `TypeError` in every browser. No browser has ever called this route, so nothing caught it. Identity also sets `user.name` and `user.displayName` to the user's UUID, which the browser's passkey picker would show.
2. **No `excludeCredentials`.** Identity computes it for operators (`operator.ts`, `excludeExisting: true`), but the route drops it. An operator can then register their second passkey on the same authenticator. The passkeys are discoverable, so the device keeps only the newer one while the server counts two: the two-passkey rule of §11.4 is met on paper only.

## Scope

In:

- `apps/ops` (new): `package.json`, `index.html`, `vite.config.ts` (U2), `vitest.config.ts`, `tsconfig.json`, `tsconfig.test.json` (including both config files), and `src/`. That holds the API client, the `base64url` and WebAuthn helpers, the session controller (U6, U7), the sign-in, enrolment and directory screens, the shell with its header, sign-out and error boundary, and the tests, including the build test.
- `apps/api/src/ops-routes.ts`: the register-options fields (U12). Tests: `ops-flow.integration.test.ts` for the route body, which needs the Docker test database.
- `packages/contracts/src/ops.ts`: new `passkeyRegisterOptionsResponse` and `passkeyAuthenticateOptionsResponse` schemas (with their `ops…` aliases), describing what the routes already send plus U12's fields. Both routes check their body against them in tests. `contracts` tests are updated to match.
- `apps/api/Dockerfile` (U4). `apps/api/src/image.test.ts`: the image serves the console (pin 10).
- `pnpm-lock.yaml`: the new importer only.
- `architecture.md` §8.5 Ops console row: names `apps/ops` as the bundle the service serves on the ops hostname.
- `docs/roadmap.md` (last commit): snapshot (last shipped, next chunk `ops-console-proof`), the `ops-console-ui` row **done**, the counts, and the Phase-0 line. `AGENTS.md` Repository state row.

Out:

- Passkey management (list, rename, remove, add while signed in). The API cannot list or remove a passkey; a later chunk adds both.
- Grants, revocation and recovery screens. These stay with the owner's `ops-operator` one-off (ADR 0015).
- Feature adoption, idle communities and usage (§19). These need `usage-facts` (Q17).
- Directory search, paging, organisation detail, and plan or billing data.
- A cross-tab sign-out broadcast.
- Any change to identity, `apps/admin`, the tenant routes or the static server.
- Terraform, DNS, IAM and API Gateway. No live run. Staging stays parked; `ops-console-proof` exercises the console on staging and carries AGENTS.md §6's cost duties for unparking.

## Behaviour

Every screen has the ops chrome: the product name, and for a signed-in operator the Directory link and "Sign out". Errors appear in a `role="alert"` region and status text in `role="status"`. Each page's `h1` has `tabIndex={-1}` and receives focus on a route or step change.

1. **Loading.** "Checking your session…" while U6's `me` runs.
2. **Unsupported browser.** U8.
3. **Sign in.** U10, with U9's messages. It also shows the message carried from sign-out, session end or enrolment.
4. **Enrol.** U11 and U12.
5. **Directory.** U13.
6. **Session end.** U6 (cap) and U14 (sign-out) land on sign-in with their message.
7. **Offline.** A network failure shows "Something went wrong. Try again." (U9) or the screen's own message, and changes no state. Nothing retries on its own except U7's single repeat after a 401.
8. **Crash.** U15.

## Data

No table, column or migration. The console holds the address and codes typed during enrolment in component state until the step completes or the page unloads. While signed in it holds the role keys and the directory rows. All of it is in memory only and none of it is stored.

**Accessibility (D16, WCAG 2.2 AA, a merge gate).**

- **axe in jsdom on every state:** loading, unsupported, sign-in with each message, each enrolment step and message, and directory loading, list, empty, truncated, 403 and failed.
- **Explicit tests:** focus moves to the `h1` on each change; errors are in `role="alert"`; every input has a label; the flows work by keyboard alone.
- **Not checked in jsdom:** colour contrast (axe's `color-contrast` is off, as in admin), target size (2.5.8) and focus not obscured (2.4.11). They are checked by hand in a real browser in `ops-console-proof`. Until then that gap is named and accepted.
- **Accessible authentication (3.3.8):** met by passkeys and by code fields that allow paste.

**Residency, logs and analytics.** No third-party script, font or request (the CSP enforces `'self'`). No analytics or error reporting (rule 6). The console logs nothing (rule 5, U15). The authenticator stores fixed labels, not the address (U12). The directory carries no personal data.

**Permissions.** None new. `me` is unchanged.

**Cost.** No new billed resource. The bundle adds a few hundred KiB to the image. With no refresh timer, each tab makes one `me` call on load and one refresh per 15 minutes of use, well inside the ops stage throttle (10 per second, burst 20).

## Risks

- **The CSP breaks the console in a real browser but not in jsdom.** Pins 1–3 check the built output and the rendered states. Pin 10 boots the real image. `ops-console-proof` loads the console in a real browser with the CSP and checks for violations.
- **Tabs or reloads sign the operator out.** U6 and U7 cut refreshes to one per 401 and serialise them. A lost response after the server has rotated the token is accepted as a residual risk, and it fails safe.
- **Registration fails in every browser, or a second passkey lands on the same device.** U12, pin 7. Only a real browser proves an authenticator refuses a duplicate, so this is checked in `ops-console-proof`.
- **Safari refuses a ceremony after an `await`.** Named for `ops-console-proof` (U9).
- **A token or code leaks to script storage, the URL or a log.** HttpOnly cookies (PR #63), pins 4, 5 and 9, U15.
- **The ARM image build cannot run Vite.** The lockfile already carries the `linux-arm64-gnu` bindings for Rolldown, Lightning CSS and Tailwind Oxide. CI Stage 3 builds the ARM image on every pull request.
- **Size.** About 650–800 source lines: `apps/ops` about 600–700, the route and contracts about 40, the Dockerfile about 5, config about 60. Tests are about 1,000–1,300 lines. That is around the ~800-line guide for source and over it with tests. A split into "sign-in and directory" then "enrolment" would ship a console nobody can reach, because an operator must enrol before signing in. **Owner to accept the size.**
