## Problem

Architecture §11.4: every `platform_*` role signs in with a passkey; an email code cannot start or recover a platform session; each operator holds at least two passkeys. `PLATFORM_ROLE_KEYS` are reserved (`modules/core/access/domain/role.ts:20-24`, `:39-43`), but nothing grants them, and nothing can enrol an operator's passkeys or mint a session only an operator route accepts. `ops-identity-primitives` adds session kinds, email-code purposes, per-RP passkeys and required user verification. This chunk uses them to give the identity module the operator lifecycle, as tested module functions. Routes, the one-off task and the UI come in `ops-console-api` and `ops-console-ui`.

## Definitions

- **Ops credential:** a stored passkey credential whose `rp_id` equals the ops hostname. Tenant credentials (the auth-hostname RP ID), credentials for any other RP ID, and credentials with a null `rp_id` (legacy) are not ops credentials. "Two credentials" anywhere in this spec means two ops credentials.
- **Open grant:** not revoked, not activated, and `now < enrolment_expires_at`.
- **Active grant:** not revoked and activated.
- **User lock:** `pg_advisory_xact_lock(hashtextextended('operator:' || user_id, 0))`, taken inside the transaction that changes a user's grants or operator sessions.

## Behaviour

Module behaviour; screens come in `ops-console-ui`. Every failure returns null or a typed error with no reason that distinguishes cases to a caller.

1. **Grant.** `grantOperator(userId, roleKeys, enrolmentCode)`: user must exist; each key one of the three; code at least the floor; O10 applies; under the user lock. Inserts one row per role with the same code hash and window. Appends `granted` per role. Returns the grant ids, never the code.
2. **Start enrolment.** `startOperatorEnrolment(address)`: O13. Appends `enrolment_started` only when a grant is open.
3. **Verify enrolment.** `verifyOperatorEnrolment(address, emailCode, enrolmentCode)`: O5; the enrolment code must match an open grant of the user. Never creates a user. Success: if the user already holds two ops credentials, O9 activates and no session is returned; otherwise returns an `enrolment` session (no refresh).
4. **Register.** Begin and finish with O8's options. Finish appends `passkey_registered` and, through `onStored`, activates per O9 (two ops credentials, inside the window, under the user lock) and appends `activated`.
5. **Sign in.** `finishOperatorAuthentication` calls `verifyPasskeyAssertion` (RP ID = ops hostname, `acceptLegacy: false`, UV required), then, only if the user has an active grant, `createSession({ kind: "operator", absoluteExpiresAt: now + 8 h })` and appends `signed_in`. Valid assertion, no active grant: null, `sign_in_refused`. Invalid or unknown: null, no event. It never calls `finishPasskeyAuthentication` or `verifyEmailOtp`.
6. **Read.** `readOperatorSession(accessToken)`: `readSessionWithKind` accepting only `operator`, plus at least one active grant; returns `{ userId, roles }`.
7. **Refresh.** `refreshOperatorSession(refreshToken)`: `refreshSession` with accepted kinds `["operator"]` (primitives P3) and the in-transaction check (O11): user lock, then an active grant, else no successor and null. Refuses at or after `absolute_expires_at`. The returned `expiresIn` is the stored access lifetime, so near `absolute_expires_at` it is below 900 seconds; callers in `ops-console-api` and `ops-console-ui` use it and never assume 900.
8. **End.** `endOperatorSession` revokes the session and appends `signed_out`.
9. **Revoke.** O11 and O15. Appends `revoked` per grant.
10. **Recover.** `recoverOperator(userId, roleKeys, enrolmentCode)`: O14. One transaction under the user lock: revoke (9), append `recovery_regrant`, grant (1).

## Risks

- **Email becomes an operator back door.** Needs the 128-bit owner-delivered code as well as the mailbox, inside a 24-hour owner-opened window; email never yields an operator session. Pins 1–4.
- **The enrolment code leaks in transit.** It is generated offline, travels only through the owner's secret and the owner's own channel to the operator, and the secret is force-deleted after the run (O16). It is useless without the mailbox and outside the window.
- **Two passkeys on one device.** Mitigated, not prevented (O8). Accepted by the owner.
- **Session kinds confused.** Pins 8, 14, 16; the primitives defaults fail closed.
- **A revoked operator keeps a session.** Revocation, refresh and activation serialise on the user lock; refresh requires an active grant (pins 9, 17).
- **A lost passkey comes back to life.** Revocation deletes ops credentials (O15, pin 18).
- **Single-person compromise of recovery.** Until two-person recovery exists, whoever controls the owner's account and the provision secret can grant or recover any operator. Mitigations: every recovery is recorded (`recovery_regrant`), the review date in ADR 0015, and the secret's force-delete after each run.
- **Event table abuse.** Rows only after a valid signature or an owner action (pin 11); append-only by grant (pin 12).
- **Size.** Estimated 500–600 source lines and 650–800 test lines, migration excluded. One module, about 7 tasks.
