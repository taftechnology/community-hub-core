# Spec: audit log

Slug: `audit-log`
Status: approved (2026-09-26, Abdus Salam)
Supersedes: —
Architecture refs: §6.3, §6.4, §11.4, §12.1, §12.4, §19.2; AGENTS.md §1 (1, 3, 7), §6, §7

## Problem

§19.2 requires an append-only, hash-chained audit log per organisation. Nothing in the repo can record one. Identity, jobs, and the admin app do not exist yet, so this chunk cannot seal the chain to S3 or show it to a tenant. It has to freeze the row and the hash, because the first stored digest cannot be reinterpreted later.

## Scope

**In**

- `app.audit_events`: organisation-scoped, append-only, hash-chained. First product table whose rows are evidence.
- Hash version `0x01`, computed in a `BEFORE INSERT` trigger with built-in `sha256(bytea)`. A TypeScript encoder is the other implementation of the same bytes.
- `appendAuditEvent` inside the caller's `withOrgTransaction`. A lost race on `(org_id, seq)` retries up to five times under `READ COMMITTED`, then throws.
- `verifyAuditChain` reads that organisation's rows in order and recomputes every digest in TypeScript.
- `defineAuditAction` and `defineAuditPurpose` in `@community-hub/kernel`. The event-name checker learns both, with must-fail fixtures.
- Grants and policies so the `app` role can `INSERT` and `SELECT` only.
- Architecture §12.1 (platform tables row) and §19.2 (chain rules this chunk freezes). §6.4 gains one sentence: a community move does not rewrite `app.audit_events`. No ADR.
- Roadmap, last commit of the implementation branch: `audit-log` **done**, next `api-au-skeleton`, Phase 0 `8 / 10`.

**Out** (explicitly)

- Daily chain-head seal to S3 Object Lock. No `jobs` worker, no Terraform, no bucket.
- Tenant view and export. No admin app, no HTTP route.
- Product actions. `identity-otp` is the first product caller. This chunk registers none in `src`.
- Deduplicating a retried append. There is no `idempotency_key` column.
- `pgcrypto`, or any bootstrap change to install an extension.
- A per-organisation chain-head table, an advisory lock, or `SELECT … FOR UPDATE`.
- `modules/core/audit`. No module host exists. The table and the writer stay in `@community-hub/db`, same as the outbox. Kernel holds the names only, and does not import db.
- Rewriting `withOrgTransaction` to force an isolation level for every caller.

## Behaviour

### Packages

`@community-hub/kernel` exports `defineAuditAction`, `defineAuditPurpose`, and `AUDIT_NAME_RE`. It stores the two registries in memory. It does not know about Postgres.

`@community-hub/db` owns the table, the trigger, `appendAuditEvent`, `verifyAuditChain`, and the TypeScript encoder. `appendAuditEvent` takes an `OrgTransaction`. A pooled `Sql` is not assignable to it. Gateway already cannot import this package.

### Table

Organisation-level. No `community_id`. A community the event is about is an entry in `target_ids`.

Primary key `(org_id, id)`. Named unique constraint `audit_events_org_id_seq_unique` on `(org_id, seq)`.

`id` is an application-minted UUIDv7 from `newId()`, chosen by `appendAuditEvent`. The trigger does not replace it. No column has a database default. Columns the trigger fills are `NOT NULL` so an insert without the trigger fails closed rather than storing a caller-supplied substitute.

| Column         | Type          | Null                        | Written by      | Class      |
| -------------- | ------------- | --------------------------- | --------------- | ---------- |
| `id`           | `uuid`        | `NOT NULL`                  | append          | `internal` |
| `org_id`       | `uuid`        | `NOT NULL`                  | trigger         | `internal` |
| `seq`          | `bigint`      | `NOT NULL`, `CHECK (>= 1)`  | trigger         | `internal` |
| `hash_version` | `smallint`    | `NOT NULL`                  | trigger         | `internal` |
| `prev_hash`    | `bytea`       | `NOT NULL`, length 32       | trigger         | `internal` |
| `hash`         | `bytea`       | `NOT NULL`, length 32       | trigger         | `internal` |
| `actor_kind`   | `text`        | `NOT NULL`                  | caller          | `internal` |
| `actor_id`     | `uuid`        | see actor check             | caller          | `internal` |
| `action`       | `text`        | `NOT NULL`                  | caller          | `internal` |
| `target_ids`   | `uuid[]`      | `NOT NULL`; see array check | caller          | `internal` |
| `purpose`      | `text`        | `NOT NULL`                  | caller          | `internal` |
| `request_id`   | `uuid`        | `NOT NULL`                  | request context | `internal` |
| `occurred_at`  | `timestamptz` | `NOT NULL`                  | trigger         | `internal` |

Every stored column is covered by the hash. `hash` is the digest, not an input. `hash_version` is the leading version byte of the preimage, not a second length-prefixed field.

`target_ids` may be empty. It may not contain a null element, and it has one dimension. `uuid[] NOT NULL` does not give either guarantee: `ARRAY[NULL::uuid]` is a non-null array. The check is:

```sql
CONSTRAINT audit_events_target_ids CHECK (
  CASE
    WHEN cardinality(target_ids) = 0 THEN TRUE
    WHEN array_ndims(target_ids) IS DISTINCT FROM 1 THEN FALSE
    ELSE array_position(target_ids, NULL) IS NULL
  END
)
```

`CASE` evaluates arms in order and does not evaluate the rest. An empty array stops on `cardinality` 0 (`array_ndims` of an empty array is null). A two-dimensional array stops on `array_ndims` and fails this named check. It never reaches `array_position`, which raises `searching for elements in multidimensional arrays is not supported` instead of a check violation. A one-dimensional array with a null element fails the `ELSE` arm. A null element has no hash encoding: the field is 16-byte UUIDs concatenated, and neither the SQL function nor the TypeScript encoder skips or invents a stand-in. `appendAuditEvent` rejects a list that contains a null, a hole, or a value that is not a UUID, before the insert. The check is the backstop for a raw `INSERT`.

RLS, `FORCE ROW LEVEL SECURITY`. Two policies, both comparing `org_id` to `current_setting('app.org_id')::uuid`:

- `audit_events_select` — `FOR SELECT` … `USING`
- `audit_events_insert` — `FOR INSERT` … `WITH CHECK`

No `FOR ALL`, `FOR UPDATE`, or `FOR DELETE` policy.

### Actor

`actor_kind` is `user`, `support`, or `system`, enforced by a `CHECK`. It is not a Postgres enum type, so a later kind is a check change and a new UTF-8 value in the same hash field. That does not bump `hash_version`. Adding, removing, or reordering a field does.

`actor_id` is null only for `system`. `user` and `support` require an id. The check is:

```sql
actor_kind IN ('user', 'support', 'system')
AND (
  (actor_kind = 'system' AND actor_id IS NULL)
  OR (actor_kind IN ('user', 'support') AND actor_id IS NOT NULL)
)
```

`system` uses null rather than a fixed UUID. A sentinel id would be a person-shaped value that every later join would have to exclude. In the hash, a null `actor_id` is a length prefix of 0 and no bytes.

`support` is a platform operator under a §11.4 grant, not a tenant user. `actor_id` is that operator's id. Callers must not treat the column as `identity.users.id` unless `actor_kind` is `user`. Jobs and sweepers use `system` and a null `actor_id`.

`appendAuditEvent` rejects a kind/id pair the check would reject, before the insert. The check is the backstop for a raw `INSERT`.

### Action and purpose

Both names match `AUDIT_NAME_RE`:

```text
^[a-z][a-z0-9_]*\.[a-z][a-z0-9_]*\.[a-z][a-z0-9_]*$
```

Three segments, the same character rules as `EVENT_NAME_RE`, and no `.vN` suffix. The database `CHECK` on `action` and on `purpose` uses that pattern. `defineAuditAction` and `defineAuditPurpose` throw on a name that fails it.

The two registries are separate. The same string may be both an action and a purpose. Two `defineAuditAction` calls with the same name are a checker failure, and the same for purposes.

`appendAuditEvent` throws if the action or the purpose was not registered in this process. A raw `INSERT` of a well-formed unregistered name still chains: the trigger cannot see the TypeScript registry. The supported writer is `appendAuditEvent`.

This chunk's `src` registers no product name. Tests register the names they append. The checker skips `*.test.ts`.

The event-name checker scans `defineAuditAction` and `defineAuditPurpose` under the same trees as `defineEvent`. Must-fail fixtures: a `.vN` suffix, two segments, a non-literal name, and a duplicate action name in two files. Must-pass: `audit.chain.recorded`. Zero audit declarations in the live tree is success. Existing `defineEvent` rules stay as they are.

### Hash version 0x01

Preimage, then SHA-256. The first byte is `hash_version` (`0x01`). Each field after that is `uint32` big-endian length, then the bytes. Built-in send functions are the SQL encoding: `uuid_send`, `int8send`, `int4send`, `convert_to(text, 'UTF8')`. `sha256(bytea)` is the built-in added in Postgres 11. The cell and the Docker image are 17. No extension.

| Order | Field         | Bytes                                                                         |
| ----- | ------------- | ----------------------------------------------------------------------------- |
| 1     | `org_id`      | 16-byte UUID                                                                  |
| 2     | `id`          | 16-byte UUID                                                                  |
| 3     | `seq`         | `uint64` big-endian                                                           |
| 4     | `prev_hash`   | 32 bytes. Seq 1 uses 32 zero bytes                                            |
| 5     | `actor_kind`  | UTF-8                                                                         |
| 6     | `actor_id`    | 16-byte UUID, or length 0 when null                                           |
| 7     | `action`      | UTF-8                                                                         |
| 8     | `target_ids`  | 16-byte UUIDs concatenated in array order. Empty is length 0. No null element |
| 9     | `purpose`     | UTF-8                                                                         |
| 10    | `request_id`  | 16-byte UUID                                                                  |
| 11    | `occurred_at` | `uint64` big-endian microseconds since Unix epoch, UTC, trunc toward zero     |

`occurred_at` is stored as `timestamptz`. The integer that enters the hash is `trunc(extract(epoch from occurred_at) * 1000000)::bigint`. The TypeScript encoder takes that integer as a `bigint`. It does not accept a `Date`, and it does not round to milliseconds. The trigger does not store `date_trunc('milliseconds', clock_timestamp())`.

`verifyAuditChain` selects the microseconds in SQL and returns them as text:

```sql
trunc(extract(epoch from occurred_at) * 1000000)::bigint::text
```

postgres.js returns a `timestamptz` column as a JavaScript `Date`, which has milliseconds only. `clock_timestamp()` has microseconds. Reading the column as a `Date` would build a different preimage from the one the trigger hashed, and verify would report `audit.chain.broken` on an intact chain. The frozen vector does not catch that: `2026-01-01 00:00:00+00` has a zero microsecond part.

`app.audit_event_hash(...)` is `IMMUTABLE`, with `SET search_path = pg_catalog, app` on the function, and throws if `hash_version` is not 1. The trigger calls it. `verifyAuditChain` does not. Verify uses the TypeScript encoder, so a bug in the SQL function cannot bless itself. Both implementations must equal the frozen vector below. A test that only compares them to each other is not sufficient.

Frozen input:

| Field          | Value                                          |
| -------------- | ---------------------------------------------- |
| `hash_version` | 1                                              |
| `org_id`       | `00000000-0000-7000-8000-000000000001`         |
| `id`           | `00000000-0000-7000-8000-000000000002`         |
| `seq`          | 1                                              |
| `prev_hash`    | 32 zero bytes                                  |
| `actor_kind`   | `user`                                         |
| `actor_id`     | `00000000-0000-7000-8000-000000000003`         |
| `action`       | `audit.chain.recorded`                         |
| `target_ids`   | empty                                          |
| `purpose`      | `audit.chain.test`                             |
| `request_id`   | `00000000-0000-7000-8000-000000000004`         |
| `occurred_at`  | `2026-01-01 00:00:00+00` (1767225600000000 µs) |

Digest (SHA-256, hex):

```text
7a29119e629b70f9d9ff4ef69ebc874303ee4315a745f306cbddb802c129b5ad
```

Those two names exist only as frozen inputs. They are not product registrations.

### Trigger

`BEFORE INSERT` on `app.audit_events`, one row, `SECURITY INVOKER`. It overwrites these fields on every insert, including when the statement supplied them:

- `org_id` = `current_setting('app.org_id')::uuid`
- `hash_version` = 1
- `seq` = one more than the highest `seq` visible in this organisation, or 1 when there is none
- `prev_hash` = that row's `hash`, or 32 zero bytes when `seq` is 1
- `occurred_at` = `clock_timestamp()`
- `hash` = `app.audit_event_hash` of the row it just filled

`clock_timestamp()` is the insert's clock, not `now()` / `transaction_timestamp()`. Two appends in one transaction do not share a timestamp frozen at `BEGIN`. They may still fall in the same microsecond. Their digests differ because `seq` and `prev_hash` differ.

The previous-row read is `SECURITY INVOKER` and filters on `current_setting('app.org_id')::uuid`, so it does not depend on the policy alone. `SELECT … INTO` a previous hash finds nothing on the first row of an organisation, and that variable is null. Assign `seq` and `prev_hash` with `CASE WHEN prev IS NULL THEN … ELSE … END`. The null arm is seq `1` and 32 zero bytes. The insert still writes that row.

Do not gate those assignments on `IF prev IS NOT NULL AND prev.hash <> NEW.hash`. SQL does not short-circuit `AND`. When `prev` is null, `prev.hash <> NEW.hash` is null, the `IF` condition is not true, and the genesis insert would skip the chain fields. There is no second "freeze" row. This audit row is the record, including the first one in an empty chain.

`EXECUTE` on the trigger function and on `app.audit_event_hash` is revoked from `PUBLIC` and granted to `app`. The trigger function is created with `SET search_path = pg_catalog, app`.

The overwrite test is a raw `INSERT` inside `withOrgTransaction`, not a call to `appendAuditEvent` (that function does not accept chain fields). The statement supplies a foreign `org_id`, a chosen `id`, `seq` 99, `hash_version` 9, a non-zero `prev_hash`, a digest of the wrong bytes, and `occurred_at` of `2000-01-01`. The stored row keeps the chosen `id` and has the transaction's `org_id`, `seq` 1, `hash_version` 1, 32 zero bytes of `prev_hash`, a digest that matches the encoder, and an `occurred_at` after that transaction's `transaction_timestamp()` (the test delays before the insert).

### Append and retry

`appendAuditEvent` runs inside the caller's `withOrgTransaction` and inside `withRequest`.

It reads `requestId` from the request context and rejects a value that is not a UUID. It rejects a `targetIds` entry that is null or not a UUID. It does not read `idempotencyKey`. It does not take a request id, an `org_id`, a `seq`, or a hash from the caller.

There is no deduplication. Two calls in one request with the same action and the same targets insert two rows. A retried request that reads a record again records the read again. A retried write whose business effect was a no-op still records the attempt.

Before inserting, it requires `current_setting('transaction_isolation')` to be `read committed`. Any other level throws, and the surrounding transaction fails. It does not issue `SET TRANSACTION`: `withOrgTransaction` has already run `set_config`, so the isolation level can no longer be changed. `withOrgTransaction` itself stays on the session default. Postgres's default is `READ COMMITTED`, which is the supported path. A caller who began the transaction at `REPEATABLE READ` is refused. Under `REPEATABLE READ` the retry below would keep seeing the snapshot from the first statement and would never observe the winner.

The insert sits in a savepoint. On `SQLSTATE` `23505` for `audit_events_org_id_seq_unique` only, it rolls back to the savepoint and tries again, up to five attempts. Any other error, including a primary-key collision, throws immediately. After the fifth seq conflict it throws, and that throw fails the transaction. The savepoint is what keeps a seq conflict from aborting the outer transaction on the first miss. Each retried insert is a new statement and, under `READ COMMITTED`, a new snapshot, so it sees the winner's committed row.

The losing insert blocks on the unique index until the winner commits, and only then receives `23505`. Appends in one organisation serialise behind the longest open transaction that has already inserted an audit row. This chunk does not set `lock_timeout`.

A throw from `appendAuditEvent` — unknown action, bad actor, a null or non-UUID target, missing request context, isolation, the fifth conflict, or any other database error — propagates. The caller's `withOrgTransaction` rolls back. A companion write in that transaction rolls back with it. Callers do not catch the error and continue.

### Append-only

`0000_schemas.sql` grants `app` `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on future `app` tables. The audit migration revokes `UPDATE`, `DELETE`, and `TRUNCATE` on `app.audit_events` from `app`. `identity` and `platform` receive no privileges on the table.

Tests as the `app` role: `UPDATE`, `DELETE`, and `TRUNCATE` fail.

`FORCE ROW LEVEL SECURITY` plus the absence of an update policy means the table owner (`migrator`, not a superuser, not `BYPASSRLS`) also cannot `UPDATE` while the policy set is intact. `migrator` can still drop the policy, disable RLS, and rewrite the chain so that it verifies. The RDS master bypasses RLS. The Sydney Object Lock anchor is what makes that rewrite detectable. It is out of scope. Until it exists, "tamper-evident" means tamper-evident against the `app` role.

### Verify

`verifyAuditChain(tx)` takes the same `OrgTransaction`. It loads every row of that organisation ordered by `seq` and checks, in TypeScript:

- `seq` is `1..n` with no gaps
- row 1's `prev_hash` is 32 zero bytes; each later row's `prev_hash` equals the previous row's `hash`
- `hash_version` is 1
- the stored `hash` equals the TypeScript encoder over the stored columns, with `occurred_at` passed as the microsecond `bigint` selected above, never as a `Date`

An empty chain verifies. The first failure throws an error whose code is `audit.chain.broken` and which names the `seq`. The error carries no action, purpose, or other ids.

The read is one statement, so it is one snapshot. It does not lock rows. Concurrent appends do not block it, and it does not block them.

This full read is the behaviour until a seal exists. The seal chunk replaces it with a range check forward from a sealed head. This function does not grow a `since` argument now.

### Community move

Rows stay in the organisation where they were appended. The move tool must not add an `UPDATE` policy and must not rewrite this table. It records the move by appending one event in the source organisation and one in the destination. §6.4's rewrite of `org_id` applies to rows that belong to the moving community. These rows have no `community_id`, and they are not those rows.

### Tenancy

Writers and `verifyAuditChain` use `withOrgTransaction`. A future seal job does the same, one organisation at a time, with no platform-role bypass. This chunk does not add that job.

Cross-organisation: org B cannot read org A's rows. Org B's first append is `seq` 1, with a zero `prev_hash`. The chains are independent.

## Data

One product table, `app.audit_events`, classified above. All columns `internal`. Identifiers, a closed `actor_kind`, and declared action and purpose codes. No name, email, note, or free text. Append-only storage cannot honour an erasure delete (§12.4); a personal field in this row would be stuck. `target_ids` is the only place a community id appears.

Migration wave: expand. New table, checks, policies, revokes, functions, trigger. Recovery is dropping those objects. Nothing else references them. No backfill. No contract wave.

Not encrypted. SQL filters and orders `org_id` and `seq`.

## Tests

**Chain**

- Frozen vector: SQL `app.audit_event_hash` and the TypeScript encoder both equal the digest in this spec.
- Two different `actor_kind` values over otherwise identical inputs produce different digests. A null `actor_id` encodes as a zero length, and that digest differs from a 16-byte id.
- Trigger overwrite test, as written under Trigger.
- Two appends in one transaction get `seq` 1 and 2, different hashes, and neither stores a caller-supplied `occurred_at`.
- Append, then read `trunc(extract(epoch from occurred_at) * 1000000)::bigint::text`. If that integer is divisible by 1000, append again, up to a small bound, until the microsecond part is non-zero. `verifyAuditChain` succeeds. Flooring those microseconds to the millisecond produces a different digest from the stored `hash`.
- Raw `INSERT` of `ARRAY[NULL::uuid]` fails `audit_events_target_ids` (`23514`). Raw `INSERT` of a two-dimensional `uuid[]` fails that same check, and the error is not the multidimensional `array_position` error. `appendAuditEvent` with a null target throws before insert.
- One transaction appends and stays open. A second append in the same organisation blocks on `audit_events_org_id_seq_unique`. The first commits, the second receives `23505`, retries, and commits as `seq` 2. The test shows the second attempt happened. `verifyAuditChain` accepts the chain. A and B use the `hub` PgBouncer alias. The wait is observed from a third connection (`hub` again, or the direct URL), not from inside either open transaction. `hub_bleed` and `hub_reuse` are `pool_size=1` and cannot host this test.
- Org B's chain starts at `seq` 1. Org B cannot select org A's rows.
- `verifyAuditChain` on an empty organisation succeeds.
- Privileged connection flips one byte of a stored `hash`. `verifyAuditChain` as `app` throws and names that `seq`. The test does not drop RLS to make the point; the privileged connection is the existing superuser path.

**Append rules**

- Outside `withRequest`, throws, and no row is written.
- `requestId` that is not a UUID throws.
- Unregistered action, and unregistered purpose, throw. A synthetic-table insert in the same `withOrgTransaction` is absent after the throw.
- `system` with an `actor_id`, and `user` with a null `actor_id`, throw from `appendAuditEvent` and fail a raw `INSERT` on the check.
- `REPEATABLE READ` (set as the first statement of that transaction) throws before insert.
- A fake insert that always raises `23505` on `audit_events_org_id_seq_unique` is attempted five times and then throws. A `23505` on the primary key throws on the first attempt.
- Two appends with the same action and the same `target_ids` in one request insert two rows.

**Grants and RLS**

- Journal SQL contains the `REVOKE` of `UPDATE`, `DELETE`, and `TRUNCATE`, both policies, `FORCE ROW LEVEL SECURITY`, the trigger, `CASE WHEN`, and `sha256(`. It does not contain `pgcrypto` or `IF prev IS NOT NULL AND`.
- As `app`: `UPDATE`, `DELETE`, and `TRUNCATE` fail.
- `schema-rls` sees the table (`org_id`, `FORCE ROW LEVEL SECURITY`).

**Names**

- Checker fixtures listed under Action and purpose.
- `defineAuditAction('people.person.read.v1')` throws. `defineAuditPurpose` with two segments throws.

## Contracts

- `defineAuditAction` / `defineAuditPurpose` / `AUDIT_NAME_RE`.
- `appendAuditEvent(tx, { actorKind, actorId, action, purpose, targetIds })` → `{ id, seq }`. `request_id` comes from `withRequest`. `tx` is `OrgTransaction`.
- `verifyAuditChain(tx)` → void, or throws `audit.chain.broken` with the failing `seq`.
- `appendAuditEvent` returns `seq` as a decimal string. `id` is the UUIDv7 it minted.
- `app.audit_event_hash` argument order matches the field table, prefixed by `hash_version`.
- No HTTP route, no event, no entitlement key, no website collection.

## Risks

| Risk                                                                  | Mitigation                                                                                                                                                                     |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Two inserts read the same head and the chain forks                    | Unique `(org_id, seq)`; the loser waits, then retries on a new `READ COMMITTED` snapshot; concurrent test                                                                      |
| `REPEATABLE READ` retries against one snapshot forever                | Append throws unless isolation is `read committed`; five-attempt cap                                                                                                           |
| An append waits on another open transaction in the same org           | Named in this spec. No `lock_timeout` in this chunk. The wait ends at that transaction's commit                                                                                |
| Caller-supplied `seq` or `hash` forges a link                         | Trigger overwrites `org_id`, `hash_version`, `seq`, `prev_hash`, `occurred_at`, and `hash`; overwrite test                                                                     |
| `app` default privileges include `UPDATE` and `DELETE`                | Migration revokes `UPDATE`, `DELETE`, and `TRUNCATE`; tests as `app`                                                                                                           |
| "Tamper-evident" read as proof against the table owner                | Risks and §19.2: `migrator` or the RDS master can rebuild a verifying chain until the seal exists                                                                              |
| A name or email in a row can never be erased                          | Columns are ids, `actor_kind`, and declared codes. No free text                                                                                                                |
| Idempotent replay drops a second read in the same request             | No deduplication. Two appends, two rows                                                                                                                                        |
| `support` id joined as a tenant user                                  | `actor_kind` is in the row and in the hash. Null `actor_id` only for `system`                                                                                                  |
| Hash layout changed after the first row                               | Version byte `0x01`, frozen vector, both implementations must match the spec digest                                                                                            |
| SQL hash function and TypeScript encoder drift                        | Frozen digest in this spec, not a test that only compares the two to each other                                                                                                |
| Verify reads `occurred_at` as a `Date` and drops microseconds         | Select the microsecond `bigint` as text. Encoder takes `bigint`, never a `Date`. Test uses a row whose microsecond part is non-zero                                            |
| `ARRAY[NULL::uuid]` has no hash encoding                              | `CASE` check `audit_events_target_ids` rejects a null element and a second dimension without calling `array_position` on a multi-dimensional array. Raw insert expects `23514` |
| Direct `INSERT` of an unregistered but well-formed action             | Supported writer checks the registry. The check constraint only has the shape. Documented limit                                                                                |
| Verify scans a chain that will grow for years                         | Full scan until the seal. The seal chunk switches to a range from a sealed head. No `since` argument now                                                                       |
| Community move rewrites `org_id` and breaks both chains               | No `community_id`. No update policy. Architecture §6.4 sentence. Move appends in both organisations                                                                            |
| `pgcrypto` added to the trust surface for a hash Postgres already has | Built-in `sha256(bytea)`. Journal test fails if `pgcrypto` appears                                                                                                             |
| Five retries exhaust under a burst and fail a real operation          | The operation fails closed, which is the audit rule. The cap is five, not unbounded                                                                                            |
