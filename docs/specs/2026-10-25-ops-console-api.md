# Spec: Ops console API — ops routes, operator cookies, static serving and the directory

Slug: ops-console-api
Status: approved (2026-10-25, Abdus Salam)
Depends on: `docs/specs/2026-10-22-ops-operator-identity.md` (merged in PR #62)
Architecture refs: §8.5 (`architecture.md:484`), §11.4, §12.1, §17, §19 Ops console; ADR 0009, ADR 0015; AGENTS.md §1 rules 1, 2, 5, 8; §3 (split), §6 API and UI, Tenancy and data, Cost

## Problem

The identity module can grant, enrol, register, sign in, refresh, read, end, revoke and recover operators (PR #62), but nothing calls it over HTTP. The ops hostname already reaches the regional service through its own API Gateway stage (`infra/modules/aws-ingress/main.tf:124-127`, `:208-257`, `:374-414`), and the gate already has an `ops` surface (`apps/api/src/gate.ts:3`, `:155-210`), but no route uses it, nothing can serve the console's pages, and there is nothing an operator could read once signed in.

This chunk gives `ops-console-ui` what it builds on: ops routes over the operator functions, cookie-held operator sessions, static serving of a bundle on the ops hostname, and a read-only directory.

## Split (owner to confirm)

The first draft also held the `ops-operator` one-off, its runbook and the PR #62 follow-ups. That touched three modules (`apps/api`, tenancy, identity) and was estimated at 1,700–2,000 changed lines, which AGENTS.md §3 says to split. Proposed order:

2. **`ops-operator-oneoff`** (next spec): the `ops-operator` one-off, the `provision-owner` shape refusal, `docs/runbooks/ops-operator.md` (including recovery, required before first production use by ADR 0015), and the PR #62 follow-ups in identity (`signed_out` only when a row was revoked; stop exporting `lockOperatorUser` and `appendOperatorEvent`). `apps/api` and identity. It has no code dependency on this chunk.
3. **`ops-console-ui`**, then **`ops-console-proof`**.

## Behaviour

All ops routes are `surface: "ops"`: on any other host the gate answers 404 (`gate.ts:172`), and tenant routes answer 404 on the ops host (`gate.ts:175`). Failures carry no body and no reason that tells cases apart. Bodies are JSON, at most 4096 bytes (`server.ts:19`). Byte fields are base64url, as on the tenant passkey routes (`auth-routes.ts:89-94`).

1. **Enrol.** `POST /v1/ops/enrolment/start` `{email}` → 204 (A8). `POST /v1/ops/enrolment/verify` `{email, emailCode, enrolmentCode}` → `200 {"status":"enrolment"}` and sets `__Host-ops_at` (enrolment) and clears `__Host-ops_rt`; or `200 {"status":"activated"}` with both cookies cleared (the user already holds two ops passkeys and now signs in); or 401 with both cleared; a malformed body is 400.
2. **Register a passkey.** `POST /v1/ops/passkey/register/options` → 200 options, or 401 (no cookie, or no qualifying session and grant). `POST /v1/ops/passkey/register/verify` `{clientDataJSON, attestationObject}` → `200 {"activated": bool}`, 400, or 401 (A9). The UI flow: register the first passkey, then the second; on `activated: true` go to sign-in. The UI holds enrolment progress in memory; a reload during enrolment returns the user to the start (the enrolment code still works inside the window, operator spec O4).
3. **Sign in.** `POST /v1/ops/passkey/authenticate/options` → 200 options. `POST /v1/ops/passkey/authenticate/verify` `{credentialId, clientDataJSON, authenticatorData, signature}` → `200 {"expiresIn": n}` and sets both cookies; else 401 and clears both.
4. **Who am I.** `GET /v1/ops/me` → `200 {"roles": [...]}` for an operator session with an active grant; else 401. No user id or address in the body. An enrolment session gets 401.
5. **Refresh.** `POST /v1/ops/session/refresh` (refresh cookie) → `200 {"expiresIn": n}` and resets both cookies; else 401 and clears both. Near the 8-hour cap `expiresIn` is below 900; the UI schedules from it.
6. **Sign out.** A10.
7. **Directory.** `GET /v1/ops/directory` → `200 {"organisations": [...], "truncated": bool}` for an operator whose roles hold `ops.directory.view`; 401 without a valid operator session; 403 with one but without the permission (no such role today).
8. **Static.** A3 and A4. Without `OPS_STATIC_DIR` the ops host serves only the API routes.

## Data

No new table or column, no migration. ## Risks

- **A stolen operator token.** `HttpOnly` cookies; tokens never in bodies or logs. Pins 1, 4, 12.
- **Cross-site request forgery.** Exact `Origin` on every `POST`, `SameSite=Strict`, `Referrer-Policy: same-origin`. Pin 2.
- **A cookie silently dropped.** The `server.ts` fix and a test with two `Set-Cookie` values. Pin 1.
- **Sign-out that does not end the session.** The access cookie stays while the browser is open, and `endOperatorSession` finds an expired row. Pin 11.
- **Sessions that outlive the browser.** Session cookies end with the browser; the server expiries bound everything else.
- **Static serving widens the surface.** Exact routes from a boot listing, allow-list, fail-closed boot, ops host only, strict CSP, HSTS. Pins 9, 10.
- **Host confusion.** Pin 3; existing gate tests stay.
- **Enrolment start as an oracle or a crash.** Detached call with a mandatory catch. Pin 6.
- **Unauthenticated challenge rows.** `authenticate/options` and detached enrolment starts do work with no session, bounded by the stage throttle and the challenge expiries; there is no app-level rate limit (there is none for tenant routes either). Accepted; named.
- **CSP breaking the UI.** A4's build constraints are handed to `ops-console-ui`.
- **Size.** Estimated 650–800 source lines (routes ~300, cookies and Origin ~100, static ~170, gate ~40, server ~15, directory ~50, contracts ~60) and 800–1,000 test lines. Two packages of code (`apps/api`, tenancy) plus contracts.
