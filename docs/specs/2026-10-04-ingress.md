# Spec: Ingress

Slug: ingress
Status: draft
Architecture refs: §7, §7.3, §12, ADR 0009. Implements the ingress row named in `docs/specs/2026-10-03-personal-data-on-aws.md`. That spec is not edited. ADR 0009 is not edited.

## Problem

Foundations left the task security group with no inbound rule. The tree has no Route 53 zone, no API certificate, no Cloud Map namespace, no VPC link, no HTTP API, and no ECR repository for the service image. The parent spec's ingress cannot be planned.

The service chunk builds the image and the process. It needs a fixed container contract, a hostname it can trust, and an ops API it can tell apart from tenant traffic. This chunk writes that contract. The service chunk conforms to it and does not edit this module.

## Scope

**In**

The first task rewrites the task and RDS security groups in `infra/modules/aws-network` to standalone rules only, and adds the `terraform-invariants` check for those arguments. This chunk sets `db_name = "communityhub"` on the RDS instance. One module, `infra/modules/aws-ingress`, is called from the AU root in this chunk. There is no later task that wires the root, and the service chunk does not edit the ingress module.

With the image unset, the plan contains the Cloud Map private namespace, the Cloud Map service (`SRV`), the VPC link on both private subnets, two HTTP APIs, their integrations, their `$default` stages, and the ECR repository. It contains no task definition and no ECS service. Staging also attaches the certificate and the alias records, because that zone already answers. Production creates its hosted zone and does not attach records or a certificate.

With the image set, the plan adds the task definition, the ECS service, the `SRV` registration, the task-group inbound rule, and the pull policy. Desired count defaults to zero, so a set image still plans no running task.

**Out**

- Any `terraform apply`. This chunk does not apply.
- The container image, the process, the `KmsPort` reshape, and TLS `verify-full`. The service chunk does those, against the interface in Contracts.
- The production zone's records, its CAA values, its certificate validation, and the nameserver change. The production cutover does those, after the inventory in Out-of-band.
- DNSSEC, and the CloudFront certificate in `us-east-1`.
- A load balancer, a NAT gateway, a private CA, and a second interface endpoint.
- Container Insights.
- Editing `docs/specs/2026-10-03-personal-data-on-aws.md`, its plan, or a merged ADR.
- Rewriting the withdrawn apply order in `docs/runbooks/apply-staging-au.md`. This chunk adds prerequisites only.

## Behaviour

### Two APIs, one front door

A single HTTP API with one stage cannot throttle ops separately from tenant traffic, and it does not tell the process which hostname was called. This chunk uses two HTTP APIs. Both sit in `ap-southeast-2`. Both use the same VPC link and the same Cloud Map service. Both disable the default `execute-api` endpoint. Both use a `$default` stage, so the stage name is not added to the path. If a stage name other than `$default` is set, the integration overwrites the path with `$request.path`. A named stage without that overwrite fails validation.

The tenant API serves three hostnames. The ops API serves the ops hostname and has its own stage throttle and its own access log. An HTTP API has no hourly charge. The pricing page says there are no minimum fees and no upfront commitments, and that HTTP APIs are billed for the API calls received and the data transferred out ([Amazon API Gateway pricing](https://aws.amazon.com/api-gateway/pricing/), read 2026-10-04). A second API adds no monthly line. The parent spec's request price, USD 1.29 per million, stays the figure for those calls. The same calls are counted once, whether they land on one API or two.

| API    | Hostnames, under the environment zone |
| ------ | ------------------------------------- |
| Tenant | `au.api`, `auth.au`, `webhooks.au`    |
| Ops    | `ops.au`                              |

Staging names use `communityhub-staging.net`. Production names use `communityhub.one`. Alias queries are not charged. The minimum TLS version is 1.2. That check is a variable validation, so a value below 1.2 fails even when no domain name is planned. The integration timeout stays 30 seconds and the payload limit stays 10 MB. This chunk does not raise either. There is no streaming and no WebSockets. The hop from API Gateway to the task is plain HTTP inside the VPC, which the parent spec accepts.

Each integration overwrites three headers. `x-community-hub-hostname` is `$context.domainName`. `x-community-hub-client-ip` is `$context.identity.sourceIp`. `x-community-hub-request-id` is `$context.requestId`. The mapping is an overwrite, so a value sent by the client is replaced. Both APIs set all three. The process trusts those headers and no client-supplied copy. The access log still records no client IP.

### Throttle

Caps are shared by every caller. They cap cost. They do not isolate one parish from another.

| Scope                                       | Steady                 | Burst |
| ------------------------------------------- | ---------------------- | ----- |
| Tenant stage, `default_route_settings`      | 50 requests per second | 100   |
| Ops stage, `default_route_settings`         | 10 requests per second | 20    |
| `POST`, `PUT`, `PATCH`, and `DELETE` on `/` | 10 requests per second | 20    |
| Those four methods on `/{proxy+}`           | 10 requests per second | 20    |

`/{proxy+}` does not match `/`, so those four methods are routes on `/` and on `/{proxy+}`. `GET` and every other method stay on `$default` and inherit that API's stage cap. The tenant API carries those eight write routes. The ops API does not. Ops traffic uses `$default` only, at 10 and 20, because a few operators use it and a write route at the same numbers would not sit below that default.

The HTTP API throttling page calls the stage cap "default route throttling" and says: "Throttles are applied on a best-effort basis and should be thought of as targets rather than guaranteed request ceilings" ([Throttle requests to your HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html), read 2026-10-04). That page does not say whether a stage and its routes share one bucket. If each of the eight write routes has its own bucket on top of the tenant stage default, the worst case on the tenant API is 50 + 8 × 10 = 130 requests per second steady and 100 + 8 × 20 = 260 burst. The ops API has no extra routes, so its worst case is the stage target itself: 10 steady and 20 burst. The first staging apply measures the tenant case.

### Empty Cloud Map service

The Cloud Map service exists when no task is registered. The integration points at that service's ARN. What status and body the custom domain returns in that state is not confirmed here. The private-integration page and the VPC link page were checked on 2026-10-04. Neither states the status for a service with no instances ([Create private integrations for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-private.html), [Set up VPC links V2](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-vpc-links.html)). The first staging apply records the status and the integration error the custom domain returns when the service has no instances. This spec does not state them.

The same gap holds when the image is set and the desired count is zero: the service exists in Cloud Map and no instance is registered. The custom domain is the only name that answers once it is attached. The `execute-api` hostname does not answer. No container is contacted, because none is registered.

### Cloud Map and the VPC link

The namespace is a private DNS namespace in this VPC. Cloud Map creates the private hosted zone. The service publishes `SRV` records. An `A` record fails validation. The service uses the ECS custom health configuration (`health_check_custom_config`) and does not use a Route 53 health check. A task is discoverable only after its container health check passes.

The VPC link is created with both private subnets and its own security group. A link with one subnet fails validation. The link's subnets and security groups cannot be changed after create, so the plan includes both private subnets in staging and in production. That security group has no inbound rule. Its only outbound rule is TCP 8080 to the task group. Both are standalone rules, and the group does not set inline `ingress` or `egress`. A test asserts both. Staging tasks still use the one existing public subnet. Production tasks use both public subnets. A link with no traffic for 60 days becomes `INACTIVE`. The parent spec's unpark note stands. This chunk does not change it.

### Security groups

`aws_security_group.task` sets `ingress = []` and an inline HTTPS egress list. `aws_security_group.rds` sets `ingress = []` and `egress = []`. The same module already adds standalone rules to both groups. The AWS provider says not to mix those inline arguments with `aws_vpc_security_group_ingress_rule` or `aws_vpc_security_group_egress_rule`, because the inline arguments overwrite the standalone rules and the plan never settles ([aws_security_group](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/security_group)). An empty list is still an inline argument.

The first task removes the `ingress` and `egress` arguments from both groups. It does not leave the empty lists. HTTPS 443 to `0.0.0.0/0` becomes `aws_vpc_security_group_egress_rule`. The existing 5432 pair stays standalone. The 8080 rule this chunk adds to the task group is a standalone rule, and it is added only after that conversion.

A mocked plan cannot tell an omitted argument from `ingress = []`. `terraform-invariants` reads the HCL. It walks `resource` blocks the way it already walks keys, and it fails when the body of `aws_security_group.task` or `aws_security_group.rds` contains an `ingress` or `egress` assignment, including an empty list. Run against current `infra/modules/aws-network/main.tf`, that check fails. The must-fail fixture is the same shape, and the self-test keeps it failing after the live files are clean. The endpoint group is not part of this check.

`aws_security_group.endpoint` in the envelope module is inline only: one ingress rule, TCP 443 from the task group, and `egress = []`. It stays correct only while nothing adds a standalone rule to it. This chunk does not add one, and it does not change that resource. The envelope test asserts the module declares no `aws_vpc_security_group_ingress_rule` and no `aws_vpc_security_group_egress_rule`. A later change that needs a standalone rule on the endpoint group converts the group in that same change.

### Image and task count

Two controls.

`service_image` decides whether the task definition, the ECS service, and the pull policy exist. It defaults to null. Null plans none of the three.

The value, when set, matches the whole string `^${account}.dkr.ecr.ap-southeast-2.amazonaws.com/${name}/service@sha256:[0-9a-f]{64}$`. Account and name are this cell's. The digest is lowercase hex. Nothing follows it. A tag, a foreign registry, another region, uppercase hex, and a trailing suffix each fail validation.

`desired_count` decides whether anything runs. It defaults to zero and may stay zero while the image is set.

The task definition is `ARM64`, 0.25 vCPU and 0.5 GB, on the public subnets, with a public address. An `X86_64` definition fails validation. The cluster is created with the service. Its Container Insights setting is off.

Deployment is minimum healthy 100 and maximum 200, with the deployment circuit breaker and rollback on. That is the cap behind the parent connection budget. Staging selects `FARGATE_SPOT` through a variable. Production selects `FARGATE`. `FARGATE_SPOT` when `environment` is `prod` fails validation.

The task security group allows inbound TCP 8080 from the VPC link security group only. That rule is planned with the service. The execution role's log policy stays as foundations left it.

### ECR

No earlier row creates a repository for this image. Staging has never been applied, and the parent spec records no repository from the old design. This chunk creates `${name}/service`. Tags are immutable. Scan on push is on. The repository is not force-deleted. A lifecycle count rule keeps the 10 newest images and selects tagged images only (`tagStatus = tagged`). An index, its image, and its attestation then count as one when only the index is tagged. Untagged images are not expired by this policy, because those untagged manifests belong to the tagged index. No later row is named for that policy, and the repository exists before the first push, so the policy is here.

The pull policy is attached to the execution role when the image is set. Its actions are `ecr:GetAuthorizationToken` on `*`, and `ecr:BatchCheckLayerAvailability`, `ecr:GetDownloadUrlForLayer`, and `ecr:BatchGetImage` on this repository. The task role and the execution role do not receive `ecr:PutImage`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, or `ecr:CompleteLayerUpload`.

### DNS

Public zones are Route 53. Staging and production stay separate zones on separate domains.

`communityhub-staging.net` is not registered. A person registers it before the first staging apply. Registration creates the hosted zone. This chunk takes that zone's id and does not create a second staging zone. Because the zone is new and this certificate is the one it will serve, its CAA issue tag allows only `amazon.com`. The certificate is requested in `ap-southeast-2`, validated in that zone, and attached to the four staging hostnames.

`communityhub.one` is created by this chunk's production plan: the hosted zone, and nothing else in that zone. Records, CAA, certificate validation, and the nameserver change belong to the production cutover. A person inventories the zone first. Another certificate authority may already be issuing for names that exist today, so this chunk does not write an Amazon-only CAA record on `communityhub.one`.

Two variables keep those apart. `create_public_zone` is false in staging and true in production. `attach_public_dns` is true in staging and false in production. Staging passes the existing zone id. Attach needs a zone: the zone id input with `create_public_zone` false, or the zone this module creates. `attach_public_dns` true with no zone id and `create_public_zone` false fails validation. A zone id passed while `create_public_zone` is true fails validation. The cutover sets attach true on the created zone and does not pass a second zone id.

When `attach_public_dns` is false, the plan does not contain `aws_acm_certificate`, `aws_acm_certificate_validation`, `aws_apigatewayv2_domain_name`, `aws_apigatewayv2_api_mapping`, or the Route 53 records for validation, aliases, and CAA. `aws_acm_certificate_validation` is the resource that waits until ACM reports the certificate issued. It is absent from the production plan, so a production apply of this chunk does not wait on a certificate the new zone cannot validate. The zone resource does not wait on ACM. The cutover sets `attach_public_dns` true on the zone this chunk created, after the inventory and after the new nameservers answer. It does not create a second production zone.

Until that flag is on, production has no custom domain. Both production APIs still disable `execute-api`, so those APIs answer on no hostname. That is the production plan from this chunk.

### Logs

Access logs record method, matched route, status, latency, response size, and request id. They also record `$context.integrationErrorMessage`, `$context.integration.status`, and `$context.domainName`. Those three extend the parent spec's six fields. They hold the integration's error string, the integration status, and the hostname the client called. They are not a query string, a client IP, or a body. Without them the first staging apply cannot record the integration error, and the tenant log cannot tell its three hostnames apart. Both formats are the same. They do not record the query string or the client IP. The tenant API writes `/community-hub/${name}/api-access`. The ops API writes `/community-hub/${name}/ops-access`. Each group retains logs for 14 days. A retention of zero fails validation.

The service log group `/community-hub/${name}/service` already retains logs for 14 days, and `log_retention_days` must stay greater than zero. This chunk does not change that. Container Insights stays off, so this chunk adds no metrics charge.

## Data

No new `app` table and no new column. The ECR repository stores the image. The log groups store the fields named above. Those fields are not personal data. Queries still go through `packages/db`. This chunk adds no query.

## Risks

The VPC link's subnets and security groups are fixed at create. A plan that uses one private subnet cannot be corrected in place. The validation rejects that plan before any apply.

The production zone starts billing USD 0.50 a month when production is applied, before the cutover attaches records. That amount is already in the parent totals. Attaching DNS before the nameservers answer would leave the apply waiting on `aws_acm_certificate_validation`. Production tfvars leave `attach_public_dns` false.

An Amazon-only CAA record on `communityhub.one`, written without the inventory, could block a certificate another authority already issues. This chunk does not write that record.

Both APIs share one Cloud Map service. A registration bug affects tenant and ops traffic together. Separate throttling does not separate the tasks.

The hostname header is the only signal the process has. A caller who reaches the process without passing through these APIs does not get a trustworthy header. A missing header is refused. An ops route on any other hostname is refused. Any other route on the ops hostname is refused.

The status returned for an empty Cloud Map service is unconfirmed. Treating a guessed status as the health check would hide a real failure. The first staging apply records the real status before anything else depends on it.

The task role can still call KMS and read the three database secrets, as foundations left it. This chunk adds pull, not push.
