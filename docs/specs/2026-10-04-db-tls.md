# Spec: Required TLS on the database factories

Slug: db-tls
Status: approved (2026-10-04, Abdus Salam)
Architecture refs: §7.3, §12.3, ADR 0009. Implements the client side of TLS `verify-full` from `docs/specs/2026-10-03-personal-data-on-aws.md`. That spec is not edited. `docs/specs/2026-10-04-ingress.md` is not edited. `docs/specs/2026-09-18-packages-db.md` is not edited.

## Problem

`createAppSql`, `createIdentitySql`, `createPlatformSql`, `createDirectSql`, and `createPooledSql` take a Postgres URL and set no TLS. A password in that URL can surface in a driver error. The regional service cannot be the first place that rule is enforced, because every current caller would have to change inside that same chunk.

## Scope

**In**

- The four production factories take host, port, database, user, password, and the CA as separate values. TLS is required. There is no option to turn it off.
- A test-only plaintext module for the local Postgres in `packages/db/test/docker-compose.yml`, which has no TLS.
- The call sites that move with the signature, including `applyProductMigrations`.
- Three guards so the plaintext module cannot ship in `dist` or be imported from production source.
- A wrong-password query whose marker appears in no driver error, and in neither stdout nor stderr.
- A production factory aimed at the compose Postgres, which rejects and does not connect in plaintext.

**Out**

- `apps/api`, the kernel, the observability logger, the image, and CI's ARM build. Those stay in the regional service chunk, which waits until this chunk is merged.
- The Amazon RDS certificate bundle and its checksum. The factories do not open a file. The service chunk commits the bundle, checks the SHA-256, and passes the PEM in.
- Password re-read. A connection that fails authentication does not call Secrets Manager. The first chunk that checks out `createAppSql`, `createIdentitySql`, or `createPlatformSql` to serve a request owns that retry. No roadmap row is that chunk yet. The last commit of this chunk adds the open item below. That later spec states the one retry of `AWSCURRENT` and `AWSPREVIOUS`, that running connections stay up, and that the password and the secret string stay out of the log.
- A key cache. The regional service spec records that open item.
- A new database driver. The factories keep `postgres` at `3.4.9`.
- Editing `infra/`.

**Size**

About 1,150 changed lines, in four commits. That is past the ~800 guide. The call-site sweep and the TLS container tests both belong to this rule. Splitting them into two chunks would leave the plaintext module as the only way to connect.

1. The plaintext module, the call-site move, and migrations taking an open `Sql`. The production factories are unchanged and have no callers afterwards. About 400 lines.
2. The production factories require TLS and take separate values, with the TLS tests, the compose rejection, and the wrong-password marker. About 500 lines.
3. The lint rule, the build exclude, the `dist` test, and the must-fail fixtures. About 200 lines.
4. `docs/roadmap.md` and the repository-state line in `AGENTS.md`. About 40 lines.

## Behaviour

### Production factories

`packages/db/src/connections.ts` exports `createDirectSql`, `createAppSql`, `createIdentitySql`, and `createPlatformSql`. `createPooledSql` is no longer exported.

Each function takes:

| Field        | Type   | Use                                                                                                                                                                                         |
| ------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host`       | string | TCP host                                                                                                                                                                                    |
| `port`       | number | TCP port                                                                                                                                                                                    |
| `database`   | string | Database name                                                                                                                                                                               |
| `user`       | string | Role name                                                                                                                                                                                   |
| `password`   | string | Passed only as the driver's password option                                                                                                                                                 |
| `ca`         | string | PEM the client trusts. The client does not present it                                                                                                                                       |
| `servername` | string | Optional. The name checked against the certificate. When omitted, the factory uses `host`, except when `host` is an IP literal: then the factory throws synchronously before any connection |

The factories stay synchronous and return the driver's `Sql`. `postgres` 3.4.9 connects on the first query, so the factory returns before any TLS or authentication failure exists. The factory does not catch that failure and does not replace it.

The password is passed only as the driver's password option. It appears in no error the driver raises. The factory never builds a connection string. Callers must not log a driver error's text.

`ssl` is `{ ca, rejectUnauthorized: true, servername }`. `postgres` at 3.4.9 checks the certificate name when `servername` is set and `rejectUnauthorized` is true. There is no argument, flag, or overload that sets `rejectUnauthorized` to false or omits `ca`.

`createDirectSql` uses `max: 1` and `prepare: false`. The other three use `max: 4` and `prepare: true`. Each sets `onnotice` to a function that does nothing, so a server notice is not written out. The factories do not log.

`servername` exists so a test can open TCP to `127.0.0.1` while the certificate is checked against a DNS name. Production callers omit it. The regional service will pass `PGHOST` as `host` and omit `servername`, so the checked name is the RDS host.

### Plaintext module

`packages/db/src/plaintext.ts` exports `createPlaintextDirectSql`, `createPlaintextAppSql`, `createPlaintextIdentitySql`, and `createPlaintextPlatformSql`. Each takes a URL, sets no TLS, and keeps the same `max`, `prepare`, and `onnotice` as the production function of the same role. `createPlaintextDirectSql` is `max: 1`. The other three are `max: 4`.

The file is not `packages/db/src/testing.ts`. That file stays the type stand-in for `@community-hub/crypto/testing`.

`@community-hub/db/plaintext` is a vitest alias and a `tsconfig.test.json` path, both pointing at `packages/db/src/plaintext.ts`. It is not a key in `package.json` `exports`. The package exports stay `["."]`.

`packages/db/test/global-setup.ts`, `packages/db/test/migrate-test.ts`, and the integration tests that talk to the compose Postgres import the plaintext functions. They do not import the production factories for those connections. After that move the production factories have no callers. Their URL signatures are still in the file until the next commit.

### Migrations

`applyProductMigrations` and `applyMigrations` take an already-open `Sql`. They do not call a factory and they do not accept a URL. The advisory lock, `SET ROLE`, and the check that the session pid did not change stay on that `Sql`. The folder and table checks run before the `Sql` is used, so the existing unit test that rejects a `drizzle-test` folder paired with the product journal does not open a socket and does not pass a URL.

`applyTestMigrations` stays in `packages/db/test/migrate-test.ts`. It still takes a URL. It opens that URL with `createPlaintextDirectSql`, calls `applyMigrations` with the `Sql`, and closes it in a `finally` block.

Integration tests that call `applyProductMigrations` open a plaintext `Sql` and pass it in.

### TLS tests

The TLS tests do not use `packages/db/test/docker-compose.yml`, except the compose rejection below. That Postgres has no TLS, and the existing integration tests keep using it through the plaintext module.

The certificate tests start one `postgres:17` container, the same image as the compose file, bound to `127.0.0.1` on a host port Docker chooses. The test reads the mapped port. The container is removed when the file finishes, including after a failure. The test does not attach container logs or the container environment to an assertion message.

Before the container starts, the test generates a CA, a server certificate, and a second CA by running `openssl`. The private keys stay in a temporary directory. No private key is committed. If `openssl` is missing, the test fails. It does not skip. If `docker` is missing, the test fails. It does not skip. CI already provides both on `ubuntu-latest`. This chunk does not edit the workflow.

The server certificate's subject alternative name is `DNS:db.tls.test`. A script at `packages/db/test/postgres-tls-entrypoint.sh` copies the server key into the container, sets its owner to `postgres` and its mode to `0600`, and execs the image entrypoint with `ssl=on`. Postgres refuses a key that is group-readable or owned by root, which is how a bind mount arrives. The database user is `hub`. The database password is `local-tls-only`. Authentication is the image's password authentication, not `trust`.

The tests call the production `createDirectSql`, then run a query. The factory has already returned. TCP `host` is `127.0.0.1`. The CA, `servername`, and password vary.

| Test                    | CA            | `servername`     | Password           | Result                                                  |
| ----------------------- | ------------- | ---------------- | ------------------ | ------------------------------------------------------- |
| Wrong name              | Signing CA    | `other.tls.test` | `local-tls-only`   | The query rejects                                       |
| Wrong CA                | The second CA | `db.tls.test`    | `local-tls-only`   | The query rejects                                       |
| Right CA and right name | Signing CA    | `db.tls.test`    | `local-tls-only`   | The query completes and `SELECT 1` returns `1`          |
| Wrong password          | Signing CA    | `db.tls.test`    | `pw-marker-db-tls` | The query rejects. The marker assertions below cover it |

`openssl` is invoked as `openssl`, not through a library. The commands are:

```text
openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -subj /CN=TestCA -days 2
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj /CN=db.tls.test
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -days 2 -extfile san.cnf
openssl req -x509 -newkey rsa:2048 -nodes -keyout other.key -out other.crt -subj /CN=OtherCA -days 2
```

`san.cnf` contains `subjectAltName=DNS:db.tls.test` and `basicConstraints=CA:FALSE`. The test does not print the key files.

### Compose Postgres

One test points a production factory at the compose Postgres, `127.0.0.1` port `5432`, database `hub`, user `hub`, with `servername` `db.tls.test`. That server has no TLS. The query rejects. A plaintext connection would have completed `SELECT 1`, so the rejection is the proof the factory did not connect in plaintext.

A call with host `127.0.0.1` and no `servername` throws synchronously, before any connection. The factory uses `node:net` `isIP` to recognise an IP literal.

### Password marker

The wrong-password test is the marker test. The password it passes is `pw-marker-db-tls`, which is not the container password, so authentication fails and the driver raises. TLS has already succeeded, which is when the password is sent. The wrong-CA test does not assert the marker, because that failure happens before a password is sent.

The test captures stdout and stderr around the query. The marker is absent from both streams. It is absent from the error's message, from the error's own properties, from the error's stack, and from the error's `cause`.

### Three guards

1. ESLint rule `@community-hub/no-db-plaintext-import`, registered beside `@community-hub/no-crypto-testing-import`. From non-test source it reports an import or dynamic import whose source is `@community-hub/db/plaintext`, whose source is `./plaintext`, or whose source path ends in `plaintext.ts` or `plaintext.js`. `packages/db/src/plaintext.ts` is not treated as a test file. The rule id is added to `QUERY_RULE_IDS`, so a disable comment does not turn it off. Three must-fail fixtures live under `tooling/checks/encrypted-column/fixtures/fail/`: one imports the alias, one imports `./plaintext.js`, and one imports `./plaintext`. The encrypted-column self-test asserts each report. A fixture under `fixtures/pass/` that does not import the module produces no report.
2. `packages/db/tsconfig.json` excludes `src/plaintext.ts`, next to the existing exclude of `src/testing.ts`.
3. A test runs `tsc --build` with `outDir` pointed at a temporary directory. `packages/db/dist` is left unchanged. No emitted path in that directory is named `plaintext.js`, and no file there contains `createPlaintextDirectSql`.

## Data

No new table and no new column. No classification change.

## Rules touched

Residency. The production factories require TLS and trust only the CA the caller passes. The regional service will pass the RDS bundle. This chunk does not open a connection to RDS.

Secrets. The password is passed only as the driver's password option, and it appears in no error the driver raises. Callers must not log a driver error's text.

Children, tenancy, money. No query, no row, and no payment path.

## Contracts

Production callers use the four factories. `createPooledSql` is gone from `packages/db/src/index.ts`. `@community-hub/db/plaintext` is test-only. `applyProductMigrations(sql)` and `applyMigrations({ sql, folder, table })` replace the URL arguments.

## Risks

| Risk                                                                        | Mitigation                                                                                                                                                                                          |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A production file imports the plaintext module and ships a clear connection | The lint rule, the `dist` exclude, and the `dist` test. A second fresh-context review reads the diff for a remaining plaintext path                                                                 |
| The TLS container's key is committed                                        | Keys are generated into a temporary directory. The entrypoint script contains no PEM                                                                                                                |
| The marker leaks through a driver error                                     | The wrong-password test asserts the marker is absent from the message, the error's own properties, the stack, the cause, stdout, and stderr                                                         |
| A caller logs the driver text                                               | The spec forbids it. The factories do not log                                                                                                                                                       |
| Call sites miss the signature change                                        | The first commit moves every caller off the factories. The second commit changes the factories, which then have no callers. `pnpm typecheck` fails while a URL call to a production factory remains |

This chunk decides whether a connection can be made without TLS. It needs the second fresh-context review from AGENTS.md §2. The reviewer has not seen the implementation discussion. The PR records that pass.
