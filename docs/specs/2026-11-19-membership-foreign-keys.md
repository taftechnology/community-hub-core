# Spec: Membership foreign keys

Slug: membership-foreign-keys
Status: approved (2026-11-19, Adnan Bin Hossen)
Architecture refs: §6.3, §11.1; AGENTS.md §1 rule 2, §6 (Tenancy and data), §7, §8, §13. The contract step of `docs/specs/2026-11-14-user-invitations.md` (Out, :49).

**Sensitive chunk** (tenancy, database). It needs a second fresh-context review on a model that differs from every implementer model used in this chunk and from the reviewer agent's (AGENTS.md §2).

## Problem

A role grant or user link must belong to a member of the organisation (`User invitations`, architecture §11.1). Today only application code enforces that: `isMember` (`modules/core/access/infrastructure/membership.ts:22-33`) is called by `grantRole`, `grantCustomRole`, `linkUser` and their write helpers (`grants.ts:245`, `:324`, `:472`, `:564`, `:589`, `:700`). The database still accepts a grant or link for a user who has no membership row. Any writer that does not go through those functions can insert one. That includes a raw-SQL fixture, a later bulk import, or a new route that forgets the check. Such a row is exactly the cross-organisation grant `User invitations` closed.

## Scope

In:

- **Migration `0020`** (contract). It adds three foreign keys to `app.organisation_members (org_id, user_id)`, its primary key (`schema.ts:216`). Each is `ON DELETE RESTRICT`, like every foreign key in the access module.
  - `organisation_role_grants_member_fk` on `app.organisation_role_grants (org_id, user_id)`
  - `community_role_grants_member_fk` on `app.community_role_grants (org_id, user_id)`
  - `user_links_member_fk` on `app.user_links (org_id, user_id)`

  The migration is generated by drizzle-kit (0.31.10) from the schema change and left as generated. Drizzle emits a plain, validated `ADD CONSTRAINT … FOREIGN KEY` (27 of the 32 keys in the journal are so; the five `NOT VALID` ones, `0007:60`, `0014:33`, `0017:15`, `0019:51-52`, were hand-edited). Postgres therefore checks every existing row when it adds each key, not only new ones. No `NOT VALID` is added to these three keys and no separate `VALIDATE` section is written. If any grant or link has no membership, `0020` fails. `applyMigrations` runs all pending migrations and their journal rows in one transaction (`packages/db/src/migrate.ts:116-120` calls drizzle's `migrate`, which loops over pending migrations inside one `session.transaction`, `drizzle-orm/pg-core/dialect.js:60-71`), so nothing from that run is applied, including `0019` if it was pending in the same run, and `db-migrate` exits 1 with `migrate 23503` and no ids (`apps/api/src/db-migrate.ts:101-104`, `apps/api/src/db-ops-error.ts`). The MFK-O1 answer (Out-of-band) makes this failure the only orphan check. Rollback and recovery says what follows if it ever happens.

- **App role privileges** are unchanged. The referential check on an insert runs as the referenced table's owner (`migrator`) and bypasses row level security, so `app` needs no `REFERENCES` or extra `SELECT` on `organisation_members`. New test 1 inserts as `app`, so a missing privilege would show as `42501` rather than `23503`.

- **Schema** (`modules/core/access/db/schema.ts`): the three `foreignKey(...)` entries, `.onDelete("restrict")`, on the grant and link tables, referencing `organisationMembers.orgId` and `organisationMembers.userId`. Drizzle reads the extra-config callback lazily, so the tables keep their current order.
- **Fixtures that the keys break:**
  - `apps/api/src/users-list.integration.test.ts:1295`, pin 43 (a), inserts a community grant for a non-member by raw SQL and asserts the user is absent. It becomes a key test: the same raw insert is refused with SQLSTATE `23503` on `community_role_grants_member_fk`. Pin 43 (b) and (c) are unchanged. The users list keeps its membership condition in code, but pin 43 (a)'s weakening ("drop the membership condition", `docs/plans/2026-11-14-user-invitations.md:204`) becomes an equivalent change. With the keys, every user who holds a grant or link in the organisation has an `organisation_members` row, so dropping the `organisation_members` condition in the users-list query (`apps/api/src/access-routes.ts:550-563`) returns the same rows. The same holds for never passing a non-member id to `readUserEmails`. An equivalent change needs no weakening pin. What makes it equivalent is the database key, and new test 1 (community grants) is the must-fail test for that key. Rules touched and the PR record this.
  - `modules/core/access/infrastructure/invitations.integration.test.ts:1361-1367` inserts a user link for a random user id with no membership, to provoke `person_linked`. The test adds that membership first, through the `addMember` testing helper, and still asserts `person_linked`.
  - `packages/db/test/membership-backfill.integration.test.ts:187-212` copies the whole migration folder and appends a probe as journal `idx` 20. With a real `0020` in the folder, that would duplicate idx 20, and the real `0020` would validate against the orphans the test seeds on purpose. The copy is cut to entries `idx <= 19` before the probe is appended, the same way step 1 cuts to `idx <= 18` (`:46`). The test still asserts the exact backfill membership set.
  - `modules/core/access/db/schema.test.ts:31-38` (`accessSql()`) asserts that exactly one migration file contains `"app"."user_links"`. `0020` adds a second. The helper matches `CREATE TABLE "app"."user_links"` instead, as the people, tenancy, usage, groups and engagement schema tests do, and keeps `toHaveLength(1)`. This is a unit test, so it breaks without the Docker database.
  - Any other fixture that the full gate shows inserting a grant or link without a membership is fixed the same way, by adding the membership. No key is dropped or made `NOT VALID` to keep a fixture green. The scout found no others (every other raw insert adds the membership first).
- **New tests** (integration, Docker database), in `modules/core/access/infrastructure/membership-keys.integration.test.ts`:
  1. For each of the three tables, a raw insert in an app transaction for a user with no membership is refused with `23503` and that table's constraint name. One transaction per table (a failed insert aborts its transaction). The SQLSTATE and constraint name are read by walking the error's `cause` chain, as `grants.ts:42` does for `23505`.
  2. **Two organisations:** a user who is a member of organisation A only. A raw grant or link in organisation B for that user is refused for each of the three tables. The same insert in organisation A succeeds. This is a regression test, not a weakening pin: a key on `user_id` alone cannot be created, because `organisation_members` has no unique key on `user_id`.
  3. `ON DELETE RESTRICT`: as `migrator` (the app role has no DELETE on memberships), with `app.org_id` set by `set_config(..., true)` because `migrator` is subject to FORCE RLS, deleting a membership that a grant or link still references is refused with `23503`.
  4. The existing code paths still answer first: `grantRole` / `linkUser` for a non-member still return `not_member`, audited by `denyNotMember` (`grants.ts:205-214`; the internal writers `writeRoleGrant`, `writeCustomRoleGrant` and `writeUserLink` throw `not_member` without an audit row and are never reached with a non-member through a route). The existing membership-enforcement pins stay green, unchanged.
- **Migration test** (`packages/db/test/`): apply migrations up to `0019` in one `applyMigrations` call. As `migrator` under per-community `set_config` (as the backfill test does), insert one grant whose user has no membership. Apply `0020` in a second call. It must fail with `23503`. Afterwards the three constraints are absent from `pg_constraint`, the orphan row is still there, and the migrations table has no `0020` entry. A second database with no orphans applies `0020`, and all three constraints are present with `convalidated = true`.
- `architecture.md` §11.1 (`:668`): the membership paragraph adds that the database enforces it with foreign keys on `(org_id, user_id)` from grants and links to memberships, and that a membership cannot be removed while a grant or link references it (AGENTS.md §13).

## Behaviour

No user-visible change. Every screen and route behaves as before. A grant or link for a non-member is still refused by code with `not_member` before any insert. The answer is audited on `grantRole`, `grantCustomRole` and `linkUser` and is 422 `user_not_member` on the routes (`access-routes.ts:210-213`), so the keys are not reached through the application. They stop every other writer.

If a foreign-key violation did reach a route (a future writer without the code check), it is an unexpected database error. It takes the existing generic 500 path, and no message, SQL, constraint name or id reaches the response or the log. This chunk adds no route, so it adds no such path.

## Data

- No new table or column, and so no classification changes and no `module.manifest.ts` `dataClasses` change. Three constraints are added (Scope).
- Every key starts with `org_id` and points at a key that starts with `org_id`. A grant in one organisation can only reference a membership in that same organisation, although foreign-key checks ignore row level security.
- Grants and links are community-scoped and memberships are organisation-wide, so the key is `(org_id, user_id)` with no `community_id`. Organisation-wide membership is the rule in §11.1. The community check stays in code, as today.
- **Migration wave.** Contract. The expand step (`0019`, the table and backfill) and the code that stopped writing non-member grants both shipped in PR #86 (`290cc67`). This PR is later, as AGENTS.md §7 requires. The service on `main` writes a membership before every grant and link (`bootstrapOwner` `grants.ts:380`, accept `invitations.ts:816`), so it is compatible with the keys.
- **Record of `0019`.** As of 2026-11-19, `0019` has not been applied in any environment. Staging's last database ran `0000` to `0018` on 2026-11-09 (`admin-screens-proof`, runbook `:4565`, 19 applied). It was removed at re-park: `skip_final_snapshot` is true outside prod (`infra/modules/aws-rds/main.tf:66`), so no copy remains. The committed staging var file is parked (`enable_database = false`, `desired_count = 0`). No production database has ever been created (project owner, MFK-O1). The first environment to apply `0019` will apply `0020` in the same `db-migrate` run, on an empty database, so no row in any environment was written between the two. In that run the `0019` backfill gives a membership to every grant and link holder that exists in `identity.users` before `0020` adds the keys. On a database that already holds data, the only rows `0020` could then refuse are grants or links whose user has no identity row.
- **Rollback and recovery.** Migrations are forward-only. If the keys must go, a new migration drops the three constraints. Nothing else changes and no data is lost, and the code-level membership check stays either way. Do not roll the service image back past PR #86 (`290cc67`) while the keys exist: an older image writes grants without memberships, and those writes would fail. If `0020` ever fails with `migrate 23503` in a real environment, nothing was applied and the deployed service is unchanged. The project owner is told. A listing is written only then, as a new chunk he decides on at that time. The MFK-O1 answer does not cover that case.

## Rules touched

- AGENTS.md §1 rule 2 (tenancy): strengthened. No RLS policy, `FORCE ROW LEVEL SECURITY` or privilege changes. No `set_config` or session `SET` outside the existing test pattern.
- No entitlement key, permission, event, consent, retention or residency change.
- Security-relevant settings the plan must pin with a must-fail weakening:
  - each of the three keys exists (dropping any one from `0020` fails test 1 for that table);
  - `ON DELETE RESTRICT` (changing it to `CASCADE` fails test 3);
  - each key validated when it is added (hand-editing `NOT VALID` onto the three keys in `0020` fails the migration test: `0020` then applies over the orphan, and `convalidated = true` fails).
- Not a weakening pin, because it cannot be weakened: each key includes `org_id` (no unique key on `user_id` alone exists to reference). Test 2 is its regression test.
- Equivalent, so not pinned: the users-list `organisation_members` condition (pin 43 (a) of `docs/plans/2026-11-14-user-invitations.md:204`). With the keys it cannot change a result (Scope, Fixtures). Its must-fail test is the key test 1.

## Risks

| Risk                                                                                         | Mitigation                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An environment does hold an orphan grant or link, and `0020` fails during a deploy           | It fails before the service is deployed (migrations run first), changes nothing, and prints `migrate 23503`. Recovery is in Data (Rollback and recovery): the project owner is told and decides then whether a listing chunk is written. The MFK-O1 answer does not cover it. The Data section shows no environment can hold one today. |
| A fixture or helper still writes a grant without a membership, so the gate goes red          | Fix the fixture by adding the membership. The scout listed the two known cases, and the full gate finds the rest.                                                                                                                                                                                                                       |
| The backfill test breaks or silently stops testing `0019`                                    | It keeps its exact-set assertions. Its folder is cut to `idx <= 19`, so it never runs `0020` over its deliberate orphans.                                                                                                                                                                                                               |
| Adding the key under FORCE RLS sees fewer rows than exist, so it passes over a hidden orphan | Foreign-key checks bypass row level security (PostgreSQL manual, Row Security Policies). The migration test seeds the orphan under a community scope that the migration itself does not set, so a pass over hidden rows would fail that test.                                                                                           |
| Error text leaks ids                                                                         | `db-migrate` prints only the stage and SQLSTATE. No route gains a new database-error path.                                                                                                                                                                                                                                              |
| Lock time on deploy                                                                          | The tables are tiny or empty. A validated `ADD … FOREIGN KEY` takes `SHARE ROW EXCLUSIVE` on both tables while it scans them.                                                                                                                                                                                                           |

No staging unpark. The chunk adds no resource and costs nothing. Not verifying on the staging hostname is an AGENTS.md §8 deviation, decided by the chunk owner and recorded in the PR, as PR #86 did: there is no user-visible behaviour to verify, and the migration runs only in the Docker integration suite until a later chunk unparks staging.
