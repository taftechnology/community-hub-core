# Spec: Membership foreign keys

**Sensitive chunk** (tenancy, database). It needs a second fresh-context review on a model that differs from every implementer model used in this chunk and from the reviewer agent's (AGENTS.md §2).

## Problem

A role grant or user link must belong to a member of the organisation (`User invitations`, architecture §11.1). Today only application code enforces that: `isMember` (`modules/core/access/infrastructure/membership.ts:22-33`) is called by `grantRole`, `grantCustomRole`, `linkUser` and their write helpers (`grants.ts:245`, `:324`, `:472`, `:564`, `:589`, `:700`). The database still accepts a grant or link for a user who has no membership row. Any writer that does not go through those functions can insert one. That includes a raw-SQL fixture, a later bulk import, or a new route that forgets the check. Such a row is exactly the cross-organisation grant `User invitations` closed.

## Scope

In:

- **Migration `0020`** (contract). It adds three foreign keys to `app.organisation_members (org_id, user_id)`, its primary key (`schema.ts:216`). Each is `ON DELETE RESTRICT`, like every foreign key in the access module.
  - `organisation_role_grants_member_fk` on `app.organisation_role_grants (org_id, user_id)`
  - `community_role_grants_member_fk` on `app.community_role_grants (org_id, user_id)`
  - `user_links_member_fk` on `app.user_links (org_id, user_id)`

  The migration is generated by drizzle-kit (0.31.10) from the schema change. Its one hand edit appends ` NOT VALID` to each of the three statements, as `0007:60`, `0014:33`, `0017:15` and `0019:51-52` did (amendment A1). Adding a validated key makes Postgres run one whole-table check as `migrator`, and FORCE RLS applies the tables' policies to it: with no tenant scope, `current_setting('app.org_id')::uuid` fails with `22P02` on every database, empty ones included (Task 1 run). `NOT VALID` skips that check only. Every insert and update after `0020` is checked against the key, and a delete of a referenced membership is refused, because those per-row checks are not filtered by row level security. Rows that already exist when `0020` runs are not checked; no environment holds any (Data, MFK-O1).

- **App role privileges** are unchanged. The referential check on an insert runs as the referenced table's owner (`migrator`) and bypasses row level security, so `app` needs no `REFERENCES` or extra `SELECT` on `organisation_members`. New test 1 inserts as `app`, so a missing privilege would show as `42501` rather than `23503`.

- **Schema** (`modules/core/access/db/schema.ts`): the three `foreignKey(...)` entries, `.onDelete("restrict")`, on the grant and link tables, referencing `organisationMembers.orgId` and `organisationMembers.userId`. Drizzle reads the extra-config callback lazily, so the tables keep their current order.

## Behaviour

No user-visible change. Every screen and route behaves as before. A grant or link for a non-member is still refused by code with `not_member` before any insert. The answer is audited on `grantRole`, `grantCustomRole` and `linkUser` and is 422 `user_not_member` on the routes (`access-routes.ts:210-213`), so the keys are not reached through the application. They stop every other writer.

If a foreign-key violation did reach a route (a future writer without the code check), it is an unexpected database error. It takes the existing generic 500 path, and no message, SQL, constraint name or id reaches the response or the log. This chunk adds no route, so it adds no such path.

## Data

- No new table or column, and so no classification changes and no `module.manifest.ts` `dataClasses` change. Three constraints are added (Scope).
- Every key starts with `org_id` and points at a key that starts with `org_id`. A grant in one organisation can only reference a membership in that same organisation. The per-row checks on insert and delete are not filtered by row level security, so they see memberships of every organisation.
- Grants and links are community-scoped and memberships are organisation-wide, so the key is `(org_id, user_id)` with no `community_id`. Organisation-wide membership is the rule in §11.1. The community check stays in code, as today.
- **Migration wave.** Contract. The expand step (`0019`, the table and backfill) and the code that stopped writing non-member grants both shipped in PR #86 (`290cc67`). This PR is later, as AGENTS.md §7 requires. The service on `main` writes a membership before every grant and link (`bootstrapOwner` `grants.ts:380`, accept `invitations.ts:816`), so it is compatible with the keys.
- **Record of `0019`.** As of 2026-11-19, `0019` has not been applied in any environment. Staging's last database ran `0000` to `0018` on 2026-11-09 (`admin-screens-proof`, runbook `:4565`, 19 applied). It was removed at re-park: `skip_final_snapshot` is true outside prod (`infra/modules/aws-rds/main.tf:66`), so no copy remains. The committed staging var file is parked (`enable_database = false`, `desired_count = 0`). No production database has ever been created (project owner, MFK-O1). The first environment to apply `0019` will apply `0020` in the same `db-migrate` run, on an empty database, so no row in any environment was written between the two. In that run the `0019` backfill gives a membership to every grant and link holder that exists in `identity.users` before `0020` adds the keys. `0020` adds the keys `NOT VALID`, so it never refuses a row that already exists. Every insert or update after it is checked.
- **Rollback and recovery.** Migrations are forward-only. If the keys must go, a new migration drops the three constraints. Nothing else changes and no data is lost, and the code-level membership check stays either way. Do not roll the service image back past PR #86 (`290cc67`) while the keys exist: an older image writes grants without memberships, and those writes would fail. `0020` does not fail on existing rows. Validating the keys later needs a migration that runs the check outside FORCE RLS. That is a project-owner decision, recorded as an open item.

## Amendments

- **A1 (2026-11-19, Adnan Bin Hossen).** The keys are added `NOT VALID`, not validated. Task 1 showed that adding a validated foreign key to a table with `FORCE ROW LEVEL SECURITY` fails with `22P02` on every database. Postgres's whole-table check runs as `migrator` under the tables' policies, and `current_setting('app.org_id')::uuid` fails with no tenant scope, even on an empty table. The draft's claim that foreign-key checks bypass row level security holds for the per-row checks on insert, update and delete, not for the check that runs when a key is added. The alternative, lifting FORCE RLS on the four tables inside `0020`'s transaction, was rejected: it touches AGENTS.md §1 rule 2 and §14 for a check that has no rows to check in any environment (MFK-O1). Changed: Scope (`0020`, migration test), Out, Data, Rules touched, Risks, MFK-O1. The project owner is told, because his MFK-O1 answer approved validated keys.
