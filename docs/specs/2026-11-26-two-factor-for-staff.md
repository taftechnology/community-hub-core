## Problem

Anyone who can read a staff member's inbox can sign in to the admin as that person. Sign-in is an email code or a passkey, nothing asks for anything else, and tenant passkey sign-in does not require user verification today (`apps/api/src/auth-routes.ts:309-313`; `modules/core/identity/infrastructure/passkey.ts:203,270`). Q20 requires every admin user to set up a second factor before using the admin. Children's data access depends on it.

## Scope

In:

- A restricted pre-2FA session after an email code, and a second step: an authenticator-app code (TOTP), a user-verified passkey of the same user, or a backup code.
- Passkey sign-in with user verification on the admin sign-in screen. It counts as both factors.
- Tenant passkeys bound to the admin origin: rpId = the host of `ADMIN_ORIGIN`, origin = `ADMIN_ORIGIN` exactly, user verification required at registration and at every assertion, no legacy (null `rp_id`) credentials.
- `ADMIN_ORIGIN` read on its own in `apps/api/src/env.ts`, not only with billing, and passed by Terraform without the billing condition.
- Setup at sign-up and at the next sign-in for every user without a factor.
- Ten backup codes, shown once when the first factor is set up.
- A fresh-factor check for managing factors.
- A notice email to the account's own address when a factor is added or removed or backup codes are made. No field values.
- Settings → Security for the signed-in user, including making new backup codes.
- ADR 0022. Architecture §11.1 and §26 Q20, `docs/roadmap.md` (the `Two-factor for staff` row, Q20, a new row `Staff 2FA recovery`), ADR 0017 (a status note on point 6), and `docs/runbooks/apply-staging-au.md` updated in the same PR.

Out:

- The View of a child's field. `Children's data access` builds it on this chunk's `fresh_factor_at` and decides how a View consumes it (ADR 0017 point 5: every View needs a fresh check).
- A backup code as a fresh factor, ever.
- Remembering a device, SMS, push approval, SSO/SAML.
- Any reset of another user's second factor, by an admin or from the ops console, and recovery for a user who has lost every factor and every backup code. All of it goes to the new row `Staff 2FA recovery` (sensitive; gated before any parish goes live; single-organisation admin reset with the definer-function design, role hierarchy and session revocation, plus sole-owner and multi-organisation recovery). Until it ships, a user with nothing left cannot get back in; staging has synthetic users only.
- Operator sign-in. It already requires a user-verified passkey on the ops hostname (`modules/core/identity/infrastructure/operator.ts:816-825`).
- An HTTP rate limiter on sign-in routes (none exists). Risk.
- A retention job for `second_factor_events`. Recorded with the retention design.

## Behaviour

**Sign-in with an email code.** The code is checked as today. When it is right, the user does not get a `tenant` session. They get a restricted pre-2FA session, kind `second_factor`: 15 minutes, no refresh, accepted only by the routes marked "pre-2FA" under Contracts. It is not the operator `enrolment` kind. The admin holds the pre-2FA token in memory only. It is never written to the admin access-token key or the sign-out handle (`apps/admin/src/sign-in.tsx:63-75`, `apps/admin/src/directory.ts:27-28`). A reload loses it, and the user signs in again. "Cancel" and sign-out on the second-factor screens end it on the server. The screen moves on:

- The user has a factor: "Confirm it's you", with the choices they have set up: authenticator code (6 digits), passkey, or "Use a backup code". Default: the authenticator app if they have one, otherwise the passkey.
- The user has no factor: "Set up two-step sign-in". Authenticator app, or passkey when the service has `ADMIN_ORIGIN` and the browser has WebAuthn.

The verify answer lists the methods that apply and whether passkeys are available on this service, so the admin never offers a passkey it cannot use.

**Sign-in with a passkey.** "Sign in with a passkey" on the sign-in screen, shown when the browser has WebAuthn and the service has passkeys available (the options route answers 404 when `ADMIN_ORIGIN` is absent; the button hides on 404). The browser asks for the device PIN, fingerprint or face. A good answer gives an admin session at once, only for a tenant passkey: `rp_id` equal to the admin hostname, `user_verified` true, and the UV flag set in the assertion. Anything else gets the same refusal as a wrong passkey.

**Passkeys from before this chunk** (`rp_id` the auth hostname or null, or `user_verified` false) never count as a factor, never sign in, are not counted by the "last one" rule, and are not listed.

**Setting up an authenticator app.** A QR code rendered as inline SVG markup from the `otpauth://` link (the `qrcode` library's SVG output; the admin CSP `img-src 'self'`, `infra/modules/aws-admin-static/main.tf:3`, does not change), and the key as base32 text in groups of four. The link is `otpauth://totp/Community%20Hub?secret=…&issuer=Community%20Hub&algorithm=SHA1&digits=6&period=30`, with no account name or email, so every Community Hub account shows as "Community Hub" in the app. The user types the current code. Right: the app is set up and that step cannot be used again. Wrong: "That code didn't work. Check the time on your phone and try again." Leaving before confirming leaves nothing set up.

**Setting up a passkey.** The browser's passkey dialog, user verification required, rpId the admin hostname. An attestation without the UV flag saves nothing and gets the same answer as a failed ceremony: "The passkey wasn't saved. Try again or use an authenticator app."

**Who may set up from a pre-2FA session.** Only a user with no factor, checked at every step (TOTP start and confirm, passkey options and verify). For a user who has a factor, each of those steps answers the same 401 as a wrong code.

**Backup codes.** After the first factor, the next screen shows ten codes once, each 12 characters of RFC 4648 base32 (upper case, no padding; 60 bits) in groups of four, with Copy. "Continue" stays disabled until the user ticks "I have saved these codes". The screen says: "Keep these somewhere safe. They are the only way back in if you lose your phone or passkey." A code is accepted in any case, with or without spaces or dashes. Each works once, as the second step after an email code, and never as a fresh factor. **Recovery window (D-3).** A backup-code sign-in opens a recovery window of 10 minutes on that session (`sessions.recovery_until`). In it the user may replace or set up the authenticator app, add a passkey, remove a lost passkey (only while at least one confirmed TOTP or counting passkey stays afterwards; backup codes do not count), and make new backup codes, so someone who lost their phone or a key can set up again. Every action in it ends the user's other `tenant` and `second_factor` sessions; `operator` and `enrolment` sessions are never touched. The recovery session itself can never pass a fresh check: the fresh routes refuse it, whatever factor is used, including one set up in that session. This block belongs to that session only. After the user signs in again with the new factor, that factor works like any other, for fresh checks and, once `Children's data access` ships, the View of a child's field. Backup codes themselves never satisfy a fresh check. After a backup-code sign-in the screen says how many are left; with two or fewer left, Security shows a warning.

**After the second step or the first setup.** The pre-2FA session ends and the user gets an admin session, stored as today. The admin goes to `/` when the user holds an invitation token (the accept screen), otherwise to `/settings/users`, as `sign-in.tsx:77` does now. The token lives in a module variable (`apps/admin/src/invite-token.ts:3`), so the second-step, setup and backup-codes screens are in-app routes with no full reload, and none of them clears it; it is read only after the admin session exists.

**Wrong answers.** A wrong code, a wrong backup code, and a passkey of another user give the same 401, empty body: "That code didn't work." Each pre-2FA session allows five attempts; a right one ends the session by replacing it. At five, the session ends: "Too many tries. Sign in again." Ten wrong answers for one user within an hour, across the second step and the fresh check, refuse both for that user until the hour has passed (429, empty body, same message). The answer does not say which limit was hit.

**Fresh check.** Adding a factor, removing one and making new backup codes need a fresh factor: a TOTP code or a user-verified passkey of the user within the last 5 minutes. A passkey sign-in and a second step by TOTP or passkey count for 5 minutes after. The first setup from a pre-2FA session does not count. A backup code never does; it opens only the recovery window above. Without one, Security asks "Confirm it's you" first. Five wrong fresh answers in one admin session refuse further fresh checks in that session (429); the session itself stays.

**Settings → Security** (every signed-in user, no permission). Lists: authenticator app (set up or not, date), each tenant passkey that counts (date added), unused backup codes. Actions, each after the fresh check (replacing or setting up the app, adding a passkey, removing a lost passkey and making new codes are also allowed in a backup-code recovery window, D-3): set up an authenticator app (replaces the existing one when the new code is confirmed), add a passkey, remove the app or a passkey (refused when it is the last factor: "You need at least one way to confirm it's you"; backup codes do not count), make new backup codes (the old rows are deleted in the same transaction; the new ten are shown once). Removing a factor, replacing the app and making new backup codes end the user's other admin sessions in the same transaction (`endOtherSessions`). Each action sends the notice email. Removing a passkey id that is not the caller's gets the same 404 as an unknown id.

**Lost every factor and every backup code.** There is no way back in within this chunk (see Out). The second-step screen says: "Lost your phone and all your backup codes? You can't sign in until your account is recovered. Contact Community Hub support."

**Sessions from before this chunk.** No session made before this chunk has `factor` set. A `tenant` session counts only when `factor` is set, so every older session stops working when the new code serves traffic, and those users sign in again. No migration updates session rows.

**Offline or server error.** "Something went wrong. Try again." The pre-2FA session is kept while it lasts.

## Rules touched

- **Authentication.** A `tenant` session is created only by (a) a passkey sign-in with user verification (`factor = passkey_uv`); (b) an email code followed by a right TOTP code (`otp_totp`), a user-verified tenant passkey of the same user (`otp_passkey`), or an unused backup code of the same user (`otp_backup_code`); or (c) the first factor set up from a pre-2FA session (`otp_totp` or `otp_passkey`). `readSession` and `readSessionWithKind` refuse a `tenant` row with `factor` null. Every existing route reads with the default kinds, so a `second_factor` session is refused everywhere without change.
- **Session code edits** (`modules/core/identity/infrastructure/session.ts`): `SessionKind` gains `second_factor` (`:14`); the kind guard (`:61`) accepts it; `computeSessionExpiries` gives it refresh expiry equal to access expiry, as the enrolment branch (`:72-74`); `createSession`, `createSessionInTransaction` and `insertSession` (`:88-156`, `:428-459`) take `factor` and `fresh_factor_at`; the refresh `returning` and successor insert (`:293-330`) carry `factor`; a `second_factor` row stores a refresh hash that is never returned, and the default kinds already keep it out of refresh (`:243`); `tokens()` (`auth-routes.ts:99-109`) omits the refresh token for it; `endSession` (`:376`) accepts it.
- **Passkey code edits** (`modules/core/identity/infrastructure/passkey.ts`): every tenant call passes `acceptLegacy: false` and `userVerification: "required"` (`auth-routes.ts:221,277,310,336` and the new second-step and fresh routes); tenant finish paths require the UV flag whatever the challenge row says (`:133`, `:270`); the credential insert (`:172-182`) stores `user_verified`; tenant credential lookups (`:238-242`, `:260`) add `and user_verified` only when the caller passes a new `requireUserVerified: true` input, which only tenant calls set; operator calls (`operator.ts:833-836`) do not change, so existing ops passkeys (`user_verified` false after the migration) keep working; the second-step and fresh functions create their challenge with `user_id` = the session's user (`passkey.ts:208-209` writes null for sign-in challenges today, which stays for usernameless sign-in), and compare the credential's user with the session's user **before** consuming the challenge or writing `sign_count` (`:287-307`), and never create a session for the credential's user (`finishPasskeyAuthentication`, `:317-336`, is not reused).
- **Env** (`apps/api/src/env.ts`): the pairing check at `:174-177` splits: `ADMIN_ORIGIN` alone is accepted, `BILLING_SECRET_ARN` alone stays refused, both together are validated as now; `ADMIN_ORIGIN` validated on its own (an `https://` origin, no path); set whenever present (`:230-233` sets it only with billing); billing still needs both; the admin host joins the distinct-hostname set with API, auth, webhooks and ops (`:184-192`). Each refusal has a test.
- **TOTP.** RFC 6238, HMAC-SHA1, 6 digits, 30-second step, one step either side, constant-time compare, no reuse of a step. `$step` in the compare-and-set is the matched step (t-1, t or t+1); confirm sets it. Pinned by the RFC 6238 SHA1 vectors truncated to 6 digits.
- **Limits.** As in Behaviour; counters atomic; backup-code use and step advance atomic; user-keyed advisory lock.
- **Fresh check.** `fresh_factor_at` within 5 minutes for factor management; `recovery_until` (backup code, D-3) allows only replacing or setting up the app, adding a passkey, removing a passkey while a non-backup factor stays, and new codes. A session with `recovery_until` set never passes a fresh check, whatever factor is offered; a new sign-in with any confirmed factor clears the block. `Children's data access` must consume a fresh check per View (ADR 0017 point 5); this chunk does not relax that.
- **Permissions.** No new permission. Security needs only a `tenant` session.
- **Modules.** `core/identity` is the only domain module that changes. The notice email uses a new `OtpMail`-style port method `sendNotice({ to, kind })` (`modules/core/identity/domain/otp-mail.ts`), and the address is decrypted with `readUserEmails` (`modules/core/identity/infrastructure/user-emails.ts`) inside the identity module. The SES adapter (`apps/api/src/mail/ses-otp-mail.ts:48-54`) and `rejectingOtpMail` (`otp-mail.ts:14-18`) gain the method; the `OtpMail` fakes in `apps/api/src/ops-routes.ts` tests follow. The notice is sent after the change commits; a send failure is logged with the kind only and does not undo the change. `AuthDeps` (`auth-routes.ts:37`) gains `adminOrigin` (and the rpId derived from it), wired in `apps/api/src/index.ts` from `ADMIN_ORIGIN`; absent, tenant passkey routes answer 404.
- **Tenancy (§1 rule 2).** Identity tables have no `org_id`. No `app` table, policy, role or function changes; ADR 0004's four roles stay.
- **Residency, logs (§1 rules 1, 5).** No secret, code, `otpauth` link or email in logs, traces, errors or URLs. Error bodies stay empty. Answers carrying a secret or backup codes set `cache-control: no-store`. Mail goes through the existing provider from the regional service.
- **Secrets (§1 rule 8).** Fixtures use the RFC 6238 test key and generated keys only.

## Contracts

Zod in `packages/contracts`. Auth routes: surface `tenant`, billing `exempt`, auth hostname. No OpenAPI artefact exists in the repo, so none is regenerated.

**Breaking change kept in `/v1`, stated for §6:** `POST /v1/auth/email-otp/verify` changes its answer. The admin is the only client (no mobile app, no third party), it changes in the same PR, and the old answer would be the bypass this chunk closes. The PR says so.

- `POST /v1/auth/email-otp/verify` → `{ secondFactor: "verify" | "setup", methods: ("totp" | "passkey" | "backup_code")[], passkeysAvailable: boolean, accessToken, expiresIn }`, a `second_factor` session, no refresh token.
- Pre-2FA: `POST /v1/auth/second-factor/verify` `{ method: "totp" | "backup_code", code }` → 200 admin session (`accessToken`, `refreshToken`, `expiresIn`, `backupCodesLeft` after a backup code); 401; 429.
- Pre-2FA: `POST /v1/auth/second-factor/passkey/options` and `/verify` → 200 admin session; 401.
- Pre-2FA with no factor, or admin session with a fresh factor or a recovery window: `POST /v1/auth/second-factor/totp/start` → `{ secret, otpauthUri }`; `POST /v1/auth/second-factor/totp/confirm` `{ code }` → 204 (admin session) or `{ backupCodes, accessToken, refreshToken, expiresIn }` (first factor from pre-2FA).
- Pre-2FA with no factor, or admin session with a fresh factor or a recovery window: `POST /v1/auth/passkey/register/options` and `/verify`; the first factor from pre-2FA returns `{ backupCodes }` plus an admin session.
- `POST /v1/auth/passkey/authenticate/options` and `/verify`: user verification required; 404 without `ADMIN_ORIGIN`.
- Admin session: `POST /v1/auth/second-factor/fresh` `{ code }`, `POST /v1/auth/second-factor/fresh/passkey/options` and `/verify` → 204; 401; 429.
- Admin session: `GET /v1/auth/second-factor` → methods with dates, unused backup-code count, whether a fresh factor is current.
- Admin session with a fresh factor: `POST /v1/auth/second-factor/totp/remove`, `POST /v1/auth/second-factor/passkeys/remove` `{ passkeyId }` → 204; 409 last factor; 404 unknown or not the caller's. `POST /v1/auth/second-factor/backup-codes` → `{ backupCodes }` (also allowed in a recovery window). (POST, not DELETE: the tenant gateway allows `GET, POST, OPTIONS` only, `infra/modules/aws-ingress/main.tf:190-200`.)
- Pre-2FA or admin session: `POST /v1/auth/session/end` (the existing sign-out) ends a `second_factor` session too.
- No new event, entitlement key or website surface.

## Risks

- **A route accepting a pre-2FA session by mistake.** Test 1.
- **Accounts with no factor yet (D-4, accepted by the project owner for this chunk).** Whoever reads the inbox of an account with no factor can set one up and own the account, because email sign-in has no other channel. This covers every user at deploy, invitees until they accept, and every user from the Laravel import until their first sign-in. The notice email tells the real owner afterwards; it does not prevent it. The first setup does not count as a fresh factor. No clients are live. Before client import, `Staff 2FA recovery` adds an admin-issued setup code for Laravel-imported accounts.
- **Passkey of another user as the second step.** Test 5.
- **Brute force, parallel requests, replay.** Tests 6–8.
- **Lockout by an inbox holder** (ten wrong answers lock the real user out of the second step for an hour). Accepted.
- **Rolling deploy (D-5, accepted by the project owner).** While old and new tasks both serve this one deploy, old tasks can still issue and accept email-only `tenant` sessions; new tasks refuse them (`factor` null). The window is the deployment's overlap, minutes. No drain mechanism is added.
- **Apply order.** The current image refuses to start with `ADMIN_ORIGIN` and no billing secret (`env.ts:175-177`). So the new image is deployed first, and the Terraform change at `main.tf:498` is applied after it. The runbook says so.
- **No HTTP rate limiter.** Existing gap, not widened.
- **Lost everything.** No recovery until `Staff 2FA recovery`, which is gated before any parish goes live and before client import. Staging has synthetic users only.
- **Rollback.** Revert the code; the new tables and columns are unused by older code and can stay. The migration rewrites no data.
