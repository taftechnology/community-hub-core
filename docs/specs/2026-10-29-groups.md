# Spec: Groups

Slug: groups
Status: approved (2026-10-29, Adnan Bin Hossen)
Architecture refs: §6.3, §10.2, §12.1, §12.3, §10 roles (`group_leader_of`), plan key `groups.basic`. Implements the `Groups` row, the first Phase 2 journey. Depends on `people-households` and `usage-facts`, both on `main`. Staging stays parked.

## Problem

A parish cannot record who belongs to which ministry or group, who leads it, or hand a leader a roster. Architecture §6.3 and the module catalogue name a `groups` module and a `group_leader_of(group)` relation. Neither exists. Later journeys (Broadcast Messages to a group, Events by ministry, the mobile Parish Hub ministries list) all need groups to exist first.

It is the only way groups touches `app.persons`, because cross-module access goes through `public/` only. For each id it returns `{ personId, isMinor, givenName, familyName }`, and omits ids that are not in the current community (the caller treats a missing id as `person_not_found`). Adults' names come from the clear columns. A minor's name is decrypted only when `includeRestricted` is true; otherwise the minor's entry carries `isMinor: true` and no names. It never decrypts date of birth, email or phone. Household keys are opened once per household. It writes one `people.person.read` audit event with all returned ids as targets, only when it decrypted something. `actorUserId` is required (no null), so a restricted read always has an actor. People imports nothing from groups. Tags stay in people; this chunk does not move them.

No `entitlement` field: no manifest sets one, and people declares its plan keys through `features`. `groups.basic` is already in the plan catalogue (architecture.md:607).
- Usage producer: `createGroup` calls `recordSuccess(tx, "groups.basic", now)` as its last statement, after the audit append, same as the `usage-facts` rule.
- `apps/api/Dockerfile` and `apps/api/src/image.test.ts` are not touched: `apps/api` has no dependency on groups and no route imports it. The plan re-checks this; a route chunk adds the filter.
- `architecture.md`: the module catalogue row and §12.1 note say what shipped (see Decisions). The last commit updates `docs/roadmap.md`: `Groups` **done**, snapshot, next chunk.

## Behaviour

- A **group** has a name, an optional description, a kind (`ministry` or `group`) and a status (`active` or `archived`). Names are unique per community among **active** groups, compared on `name_key`: trim, collapse internal whitespace to one space, Unicode NFC, then lowercase, in one shared TypeScript function used by create, edit and restore. Creating a second active group with the same name fails with `GroupsError("duplicate_name")`. An archived group's name can be reused.
- Archiving keeps memberships. It blocks adding members and editing roles. Restoring fails with `duplicate_name` if an active group has taken the name.
- A **membership** links one person to one group with a role, `leader` or `member`. A person has at most one membership per group. Adding twice fails with `GroupsError("already_member")`. Removing a person who is not a member is a no-op that returns `false`. A group may have zero leaders.
- The person must exist in the same community. `addMember` calls `readRosterNames` with `includeRestricted: false` to check existence, so a person id from another community or organisation fails with `GroupsError("person_not_found")` and gives no hint which. The lookup is by the scoped transaction, never by an argument.
- **Minors may be members.** Group membership is `internal` (§12.1). A minor's group membership is held in the same table, but no function in this module returns a minor's name, email or phone. `listMembers` returns person id, role and `isMinor`. Names are not part of it.
- **Roster export** returns CSV text with the header `given_name,family_name,role` and one row per member, ordered by family name then given name then person id, so the output is deterministic. Adults' names come from the clear `given_name` and `family_name` columns. Minors are **omitted** unless the caller passes `includeRestricted: true`. The caller sets that only after checking `people.restricted.read`; the groups module cannot check permissions itself, and the export also requires the actor's user id so the audited read has an actor. With the flag, minors' names come from `readRosterNames`, which audits the read. Rows are sorted in TypeScript after decryption, because a minor's name is ciphertext in SQL.
- Every export writes one `groups.roster.exported` audit event with the group id as target and the purpose registered above. The event carries ids only: no name, no row count in the action text. The CSV is returned to the caller; the module does not store it.
- Cells that begin with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with a single quote, and every cell is double-quoted with embedded quotes doubled, so a name cannot become a spreadsheet formula. A name containing a comma, quote or newline round-trips.
- Empty states: a group with no members exports the header only. Listing groups in a community with none returns an empty list.
- No offline behaviour; there is no UI.

## Data

New `app` tables, both community-scoped. Every column is added to `dataClasses` and `manifest.test.ts` in the migration task.

`app.groups`

| Column         | Type                                                      | Class    |
| -------------- | --------------------------------------------------------- | -------- |
| `org_id`       | `uuid not null`                                           | internal |
| `community_id` | `uuid not null`                                           | internal |
| `id`           | `uuid not null`                                           | internal |
| `name`         | `text not null`, check length 1–120                       | internal |
| `name_key`     | `text not null`, normalised `name` computed in TypeScript | internal |
| `description`  | `text`, check length ≤ 2000                               | internal |
| `kind`         | `text not null`, check in (`ministry`, `group`)           | internal |
| `status`       | `text not null`, check in (`active`, `archived`)          | internal |
| `created_at`   | `timestamptz not null`                                    | internal |
| `updated_at`   | `timestamptz not null`                                    | internal |

- Primary key `(org_id, id)`. Partial unique index `(org_id, community_id, name_key) where status = 'active'`. It starts with `org_id`.
- `name` and `description` are `internal`, not encrypted: SQL must compare names for uniqueness and list them (§1 rule 3). A group name is organisational, not personal. A group name must not carry a child's name; the UI chunk adds the guidance, and the spec for any public exposure re-checks it.

`app.group_members`

| Column         | Type                                           | Class    |
| -------------- | ---------------------------------------------- | -------- |
| `org_id`       | `uuid not null`                                | internal |
| `community_id` | `uuid not null`                                | internal |
| `group_id`     | `uuid not null`                                | internal |
| `person_id`    | `uuid not null`                                | internal |
| `role`         | `text not null`, check in (`leader`, `member`) | internal |
| `added_at`     | `timestamptz not null`                         | internal |

- Primary key `(org_id, group_id, person_id)`. Foreign keys `(org_id, group_id)` to `groups` and `(org_id, person_id)` to `app.persons`, both `on delete restrict`. Both start with `org_id`. No other unique key.
- Row level security `community_isolation` on both tables, `FOR ALL TO public`, `USING` and `WITH CHECK` both `org_id = current_setting('app.org_id')::uuid and community_id = current_setting('app.community_id')::uuid`. `FORCE ROW LEVEL SECURITY`.
- Grants: the `0000_schemas.sql` defaults, then `REVOKE TRUNCATE` on both and `REVOKE DELETE ON app.groups`. `SELECT`, `INSERT` and `UPDATE` stay on both tables. `DELETE` stays on `group_members` because removal deletes the row. `identity` and `platform` get nothing.
- No column is encrypted. Foreign keys and unique keys ignore row level security, so the community of the person is also checked in code (`person_not_found`), and a test pins it. People's `persons` already revokes `DELETE`, so `restrict` is consistent. No blind index or derived clear column is needed except `name_key`, which is a derived clear column by §12.2.1 because SQL must enforce uniqueness on it.

## Rules touched

- Tenancy: two new `app` tables with `org_id`, `community_id`, row level security and `FORCE`. Scope from the transaction only; no function takes an organisation or community as an argument.
- Children (§1 rule 4, §12.3 rules 3 and 9): minors can be members; the table has no name or contact column; the export omits minors by default; a restricted export reads names through the audited `readRosterNames`; no function exposes a minor's date of birth, email or phone. No path makes a minor visible publicly.
- §1 rule 5: errors are fixed codes. Audit events carry ids only. The CSV is not logged.
- Permissions: `groups.manage` and `groups.export` are declared. This chunk does not enforce them (no routes); callers check. Entitlement `groups.basic` is declared in the manifest; the calling route will gate on it.
- Residency, consent, retention: none new. Retention of memberships follows person erasure, handled by the `restrict` foreign key; a later privacy chunk defines the purge.

## Decisions this chunk records

Recorded in `architecture.md` in the same PR.

1. **Groups is a separate feature module** under `modules/features/groups`, not part of `people`, matching architecture.md:351 and the module catalogue. It is not core, so §10.2's "core modules are never entitlement-gated" is untouched. The plan key `groups.basic` gates it. Tags stay with people.
2. **Group membership of a minor is `internal`** and carries no name. The roster export is the only place a name appears, and a minor appears only for a restricted reader, through an audited read.
3. **Leadership is a fact, not a policy.** The `leader` role is stored; `groupLeaderFact` exposes it for `packages/policy`. No permission is granted by this chunk.
4. **Exports are audited by group id, not by content.** The audit trail shows who exported which roster and when; it never holds names.
5. **`readRosterNames` is the single bridge** from a feature module to `app.persons`.

## Risks

- **Cross-tenant read or write.** Scope from `current_setting` only; policy on `USING` and `WITH CHECK`; `FORCE`; tests with two organisations and two communities in one organisation. A foreign person id must be rejected in code, because the foreign key ignores row level security.
- **Minor exposed in an export.** Default omission, plus a test with a minor fixture proving no minor name appears without the flag, and that with the flag the read is audited. The flag is the caller's responsibility; a route chunk must derive it from `people.restricted.read` and never from request input. Recorded in the Open items.
- **Spreadsheet formula injection** through a name that starts with `=`. Neutralised in the CSV writer and tested.
- **Group name carrying a child's name.** Organisational text is not classified as personal. Mitigation: guidance in the UI chunk; no public exposure here.
- **Lock order and duplicates.** `createGroup` records usage last, after the audit append and outside the savepoint that wraps the insert. A unique violation (23505) is caught inside the savepoint and mapped to `duplicate_name`, so a failed create counts nothing. Two concurrent creates of one name, and a restore racing a create, both end with exactly one active group and a `duplicate_name` for the loser.
- **Trust boundary of `includeRestricted`.** It is a plain boolean from the caller. `actorUserId` is required with it so the read is attributable. The route chunk derives it from `people.restricted.read` only.
- **Packaging.** `apps/api` does not depend on groups, so the image is unchanged. A route chunk adds the Docker filter.
- **Workspace.** The new package must be in `pnpm-workspace.yaml` and the lockfile, or it is not built or tested.
- **Schema loader.** `groupsTables` imports no value from `@community-hub/db`; `generate.test.ts` covers it.

## Tests

- Unit: name normalisation (padding, internal runs of spaces, NFC versus NFD, case), CSV escaping (comma, quote, newline, leading `=`, `+`, `-`, `@`), deterministic ordering, input validation.
- Integration (Docker test database):
  - Concurrent create of one name, and restore racing a create (no sleeps; the `pg_stat_activity` lock-wait pattern from `usage-facts`).
  - `readRosterNames`: other-community id omitted; minor names absent without the flag; with the flag decrypted once per household and audited; date of birth, email and phone never returned.
  - Create, edit, archive and restore. Duplicate active name rejected case-insensitively. Archived name reusable. Restore blocked by a taken name.
  - Add, remove, role change. Duplicate member rejected. Archived group rejects adds.
  - Two organisations, and two communities in one organisation: no read or write crosses. A person from another community is `person_not_found`.
  - Export: adult-only roster; minor omitted by default; minor included with the flag; a `groups.roster.exported` event and a `people.person.read` event exist; audit rows hold no name.
  - Privileges: `app` cannot `DELETE` from `groups` or `TRUNCATE` either table; `relforcerowsecurity` true on both.
  - `createGroup` adds one to `groups.basic` usage; a failed duplicate adds nothing.
- Schema: column lists, primary key order starting with `org_id`, policy text parsed from the migration SQL, no `pgSchema` in the schema source.
- Boundaries: groups imports people only through its public entry; people imports nothing from groups; staging stays parked.
- Manifest: whole-manifest `toEqual`; `dataClasses` covers every column.
- Settings the plan must check by weakening source: the community predicate, `FORCE`, `REVOKE DELETE` on `groups`, the person-in-community check, the minor omission, the audit append on export, the CSV formula guard, and the usage call position.
