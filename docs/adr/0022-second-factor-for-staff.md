# ADR 0022: Second factor for staff

- Status: accepted (2026-11-26, Abdus Salam)
- Date: 2026-11-26
- Spec: docs/specs/2026-11-26-two-factor-for-staff.md
- Plan: docs/plans/2026-11-26-two-factor-for-staff.md
- Refines: [ADR 0017](docs/adr/0017-childrens-data-access.md) point 6
- Amends: architecture §11.1 (second factor for tenant users) and §26 Q20

## Context

ADR 0017 point 6 requires every admin user to set up a second factor (an authenticator app, a passkey or a code sent by email), and the fresh check before a Community Admin views a child's field depends on it. Before this chunk an email code alone gave an admin session, and tenant passkey sign-in did not require user verification, so anyone who could read a staff member's inbox could sign in as that person. An email code is also the first step of sign-in, so it cannot be a second factor. The project owner (Abdus Salam) answered D-1 to D-5 on 2026-11-26. The chunk owner (Adnan Bin Hossen) decided on the same day that the second factor is passed once per sign-in, that TOTP is built on `node:crypto`, that the set-up screen uses the `qrcode` library, and that this is one chunk.

## Decision

1. **The factor rule (D-1).** A second factor is an authenticator app (TOTP: RFC 6238, HMAC-SHA1, six digits, 30-second step) or a passkey with user verification. An email code is not a second factor. A passkey with user verification required counts as both factors, so a passkey sign-in needs no second step. A user who has a factor passes it once per sign-in.
2. **A restricted session after the email code.** A right email code gives a session of kind `second_factor`: 15 minutes, no refresh token, accepted only by the second-step, set-up and sign-out routes. It becomes an admin (`tenant`) session only through a right TOTP code, a user-verified passkey of the same user, an unused backup code, or the first factor set up from it (only for a user with no factor). Every `tenant` session records the `factor` that made it (`passkey_uv`, `otp_totp`, `otp_passkey` or `otp_backup_code`), and a `tenant` session with no `factor` is refused, so every session from before this chunk stops working when the new code serves traffic. Each restricted session allows five attempts. Ten wrong answers for one user within an hour, across the second step and the fresh check, refuse both for that user.
   - Status note (O1, project owner, 2026-11-28): a correct fresh check (`freshCheckTotp` or `verifyFreshPasskey`) gives back the one attempt it took, never below 0, so only refused codes count towards the five. The five-attempt session limit and the ten-failure hourly limit are unchanged. `Children's data access` needs this, because each View uses up a fresh check and a Community Admin may View many fields in one session.
3. **Backup codes are sign-in recovery only (D-3).** Ten single-use codes of 12 characters (RFC 4648 base32) are shown once when the first factor is set up, and new ones are made while signed in. A backup code is a second step and never a fresh factor. A backup-code sign-in opens a recovery window of 10 minutes on that session. In it the user may replace or set up the app, add a passkey, remove a lost passkey (only while a confirmed app or a counting passkey stays) and make new codes. Each of those ends the user's other `tenant` and `second_factor` sessions, and `operator` and `enrolment` sessions are never touched. The recovery session itself never passes a fresh check, whatever factor is used, including one set up in it. That block belongs to the session only: after the user signs in again with the new factor, the factor works like any other.
4. **The fresh check.** Adding a factor, removing one and making new backup codes need a TOTP code or a user-verified passkey of the same user within the last 5 minutes (`sessions.fresh_factor_at`). A passkey sign-in, and a second step by app or passkey, count for 5 minutes after. The first set-up from a restricted session does not count, a backup code never does, and a recovery session never passes one. `Children's data access` consumes a fresh check per View under [ADR 0017](docs/adr/0017-childrens-data-access.md) point 5; this ADR does not relax that.
5. **Tenant passkeys on the admin origin.** The rpId is the host of `ADMIN_ORIGIN` and the origin is `ADMIN_ORIGIN` exactly. The admin host is kept distinct from the API, auth, webhooks and ops hostnames, and start-up checks that. User verification is required at registration and at every assertion, and the credential records `user_verified`. A passkey from before this chunk (an auth-hostname or null `rp_id`, or not user-verified) never counts as a factor, never signs in and is not listed. Operator passkeys do not change. Tenant passkey routes answer 404 when `ADMIN_ORIGIN` is not set, and `ADMIN_ORIGIN` is now read on its own, with or without a billing secret.
6. **The admin reset is deferred (D-2).** The project owner chose to ship with backup codes and their regeneration. An admin reset of another user's second factor, sole-owner and multi-organisation recovery, and recovery for a user who has lost every factor and every backup code move to the roadmap row `Staff 2FA recovery`, gated before any parish goes live. That row designs a definer function owned by a fifth database role, a role hierarchy and session revocation. ADR 0004's four roles do not change here.
7. **Two accepted windows.** (D-4) A user with no factor sets one up from a restricted session, and email sign-in has no other channel, so whoever reads the inbox of an account with no factor can claim it. That covers every user at deploy, invitees until they accept, and every Laravel-imported user until their first sign-in. The first set-up does not count as a fresh factor, a notice email tells the real owner afterwards, and the invitation token survives the second step and set-up. The project owner accepted the window while no clients are live; before client import, `Staff 2FA recovery` adds an admin-issued set-up code for imported accounts. (D-5) While old and new tasks both serve one deploy, old tasks can still issue and accept email-only `tenant` sessions that the new tasks refuse. The window is the deployment's overlap, migration `0024` is expand-only so old tasks keep working, and no drain mechanism is added.

## Consequences

- `POST /v1/auth/email-otp/verify` changes its answer in `/v1`: it returns a restricted token and the step to take, not an admin session. The admin is the only client and changes in the same pull request, and the old answer would be the bypass this closes.
- A user who loses every factor and every backup code cannot get back in until `Staff 2FA recovery` ships. Staging has synthetic users only.
- The TOTP key (`totp_credentials.secret` and `pending_secret`) is the only new encrypted column. It is encrypted under the identity key with its own labels, read only by user id, and never queried, logged or returned after set-up. Backup-code hashes are keyed hashes of random secrets. `second_factor_events` is append-only and holds ids and event names only; its retention job waits for the retention design.
- Each added or removed factor and each new set of backup codes sends a notice to the account's own address after the change commits, with no field values. A send failure is logged with the kind only and does not undo the change.
- Ten wrong answers lock the real user out of the second step for an hour, so someone who can read the inbox can lock the user out. No HTTP rate limiter exists on the sign-in routes, and this chunk does not add one. Both are accepted.
- `ADMIN_ORIGIN` now reaches the service without a billing secret, and the image from before this chunk refuses to start in that state. So the new image is deployed before the Terraform change, and the runbook says so.
- To roll back, revert the code. The new tables and columns are unused by older code and can stay. If the Terraform change was already applied, revert it first.

## Alternatives considered

- **Keep the email code as a second factor, as ADR 0017 point 6 says.** Rejected (D-1): it is the inbox that already passed the first step.
- **A backup code as a fresh factor.** Rejected: a backup code is the way back in when the phone or passkey is lost, so it cannot also authorise changing factors.
- **No recovery window after a backup-code sign-in.** Rejected (D-3): a user who lost their phone could sign in once and never set up a new app.
- **Build the admin reset in this chunk.** Deferred (D-2): it needs a fifth database role, a role hierarchy and session revocation, and is designed together with sole-owner and multi-organisation recovery.
- **SMS, push approval, remembering a device, SSO or SAML.** Not built here. None is needed for this rule.
